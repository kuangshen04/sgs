# 事件系统基础思路

## 核心主张

事件系统不必从零发明，而是**以编程语言的函数调用为基础，在上面加一层事件语义**。

### 从函数继承的基础设施

因为事件系统构建在函数之上，天然具备：

- **父子关系** — 函数 A 调函数 B，B 是 A 的子过程。对应到事件：一个事件的处理中触发了另一个事件，形成树状的事件派生链。
- **调用栈** — 子事件返回后回到父事件继续。天然支持事件嵌套与恢复。
- **时序关系** — 函数调用的先后顺序就是事件的时序。调用顺序即因果顺序。

### 关键前提

**单线程。** 一般游戏规则是线性、顺序执行的，同一时刻只有一条结算路径在跑。不存在两条规则并发竞争的问题。这极大降低了事件系统的复杂度——不需要锁、不需要事务、不需要考虑竞态。

这条前提成立才是合理的，如果后续发现某些场景天然需要并发（比如同时结算多个独立效果），再单独处理，而不是一开始引入并发模型。

## 事件 vs 函数：颗粒度判断

### 判断标准

事件比函数多的就是**状态机 + 可追踪的事件栈**。判定标准是：

> **如果这个流程允许被外部控制/修改（挂载 trigger），就可以作为事件。否则就是函数。**

函数和事件的本质差别不在于"做了什么"，而在于"外部能否干涉它"。

| 事件 | 不是事件（纯函数/内部步骤） |
| --- | --- |
| `damage(player, 1)` — 技能可能加伤/减伤/防止 | `calculateBonus(dmg)` — 内部计算，外部无需干涉 |
| `draw(player, 2)` — 技能可能多摸/少摸 | `drawFromPile(player)` — 单张入手的实现细节 |
| `discard(player, cards)` — 技能可能改弃牌选择 | `moveToDiscardPile(card)` — 牌移动的实现 |
| `useCard(card, targets)` — 技能可能改目标/阻止出牌 | `filterTargets(card)` — 合法性校验封装 |

## 输入与输出

事件以函数为蓝本，自然也有输入和输出。

### 输入

**输入**是调用方的**意图**。通过事件数据接口定义：

```ts
// src/events/types.ts
await new GameEvent<DamageEventData>(EventType.Damage, {
  target: defender,  // 伤害目标
  source: attacker,  // 伤害来源
  amount: 1,         // 意图伤害量
}).execute(applyDamage)
```

### 输出

> **TODO: result 尚未实现。** 当前 `execute()` 返回的是原始 GameEvent 对象——调用方可以通过 `event.data` 读取修改后的参数值（如 `event.data.target.hp`），但没有结构化的收据。

输出不应是裸数值（如 `2`），而应是**事件结果收据**——一个记录了"意图经过技能链修改后实际发生了什么"的结构化对象：

```js
const result = await damage(player, 1)
// result ≈ {
//   success: true,          // 伤害是否实际造成
//   actualAmount: 2,        // 经技能修改后的实际值
//   target: player,         // 最终目标（可能被转移）
//   cause: 'damage',        // 事件类型
//   record: [...],          // 修改记录链
// }
```

输出是结构化收据而非裸数值，原因有三：

1. **调用方需要知道细节**来决定后续行为
2. **链式反应需要上下文**——后续技能要追溯伤害来源、实际值等
3. **调试与回放**——有了收据就能重现"什么意图经过什么修改变成了什么结果"

## 实现：GameEvent + 生命周期

### 核心设计决策

**事件的执行（execute）是事件对象自身的方法，而不是外部函数。** 原因是：

- 事件必须维护自己的生命周期阶段（created → executing → completed），防止同一事件被重复执行
- 子事件必须在父事件内部完成——构造函数时自动将 eventStack.top 绑定为父事件
- 这些约束可以通过 `event.phase` 在单元测试中直接验证

```ts
// src/events/GameEvent.ts
type EventPhase = 'created' | 'executing' | 'completed';

class GameEvent<T> {
  readonly type: string;
  data: T;
  private _phase: EventPhase = 'created';
  private _parent: GameEvent | null;

  constructor(type: string, data: T) {
    this.type = type;
    this.data = data;
    this._parent = eventStack.top;  // 构造时自动绑定父事件
  }

  async execute(content: (event: this) => Promise<void>): Promise<this> {
    if (this._phase !== 'created') {
      throw new Error(`Event already ${this._phase}`);
    }
    this._phase = 'executing';
    eventStack.push(this);

    try {
      await triggerSystem.trigger(`${this.type}.before`, this);
      await content(this);
      await triggerSystem.trigger(`${this.type}.after`, this);
    } finally {
      eventStack.pop();
      this._phase = 'completed';
    }
    return this;
  }

  getParent(name: string): GameEvent | null { ... }
}
```

### content 的职责归属

**content 不作为事件构造参数，而是作为 execute 方法的参数。**

理由是：content 是引擎层的游戏规则（如 `target.hp -= amount`），跟事件类型绑定，不跟事件实例绑定。同一个 `damage` 事件，无论是由杀命中还是技能效果触发，content 都相同。把 content 存进事件构造器会导致每个调用方都要 import 同一个 content 函数。

```ts
// ✅ 当前实现：content 由调用方在 execute 时传入
await new GameEvent<DamageEventData>('damage', { target, amount: 1 })
  .execute(async (event) => {
    event.data.target.hp -= event.data.amount;
  });

// ❌ 否定的方案：content 存入事件实例
new GameEvent('damage', content, { target, amount: 1 }).execute()
// 问题：每处都要传同一个 content，且不同调用方可能传不同的 content
```

## 发布订阅（Trigger）系统

### 实现

`src/events/TriggerSystem.ts` — 全局单例 `triggerSystem`，提供 `on` / `off` / `trigger`：

```ts
// 注册触发器
triggerSystem.on('damage.before', async (event) => {
  // event.type → 'damage'
  // event.data → { target, source, amount }
});

// 触发（由 GameEvent.execute 内部调用）
await triggerSystem.trigger('damage.before', event);
```

### 当前实现状态

- ✅ `on` / `off` / `trigger` 全部可用
- ✅ 按注册顺序依次执行 handler
- 🚧 **排序策略未实现** — 当前只按注册顺序，将来需要由规则引擎注入（逆时针 / 当前回合角色优先 / 等）

### 限制一：触发顺序由规则集规定

触发系统自身不做排序决策，只提供一个**排序接口**让上层的规则引擎注入顺序策略。触发系统保持**顺序无关**，承诺"按你给的顺序执行"即可。

### 限制二：订阅者和事件互动

订阅者不是"收到通知然后干自己的事"，而是**伸手进事件内部修改它**。

## 事件栈查询：getParent

### 实现

`src/events/GameEvent.ts` 中的 `getParent(name)` 方法。已在 GameEvent 中实现，可用。

```ts
// 古锭刀在 damage.before 中的写法
triggerSystem.on('damage.before', (event) => {
  const useCard = event.getParent('useCard');
  if (useCard && useCard.data.card.name === '杀' && event.data.target.hand.length === 0) {
    event.data.amount += 1;
  }
});
```

### 设计要点

- **有契约** — 事件名决定了数据签名，`getParent('useCard')` 的返回值结构已知
- **深度弹性** — 不关心中间隔了几层（流离、反馈等），只关心"最近的同名父事件"
- **null 安全** — 如果 damage 由技能触发而非杀，`getParent('useCard')` 返回 null，优雅降级

### 与 cause 字段的关系

两者不是非此即彼：

| 方案 | 适合的场景 |
| --- | --- |
| `event.cause`（事件自带） | 高频、确定的因果信息，如"damage 是由 card 还是 skill 触发的" |
| `event.getParent(name)`（按需查询） | 低频、特定技能的上下文需求，避免所有事件都预塞无用字段 |

## 事件执行骨架

### executeEvent

几乎所有游戏动作都遵循三段式结构：

```
before（技能拦截/修改意图）→ 核心操作（原子行为）→ after（技能响应结果）
```

当前实现为 `GameEvent.execute(content)`。调用示例：

```ts
// 伤害事件
await new GameEvent<DamageEventData>(EventType.Damage, {
  target: defender,
  source: attacker,
  amount: 1,
}).execute(async (event) => {
  // content: 只写正常操作逻辑
  event.data.target.hp -= event.data.amount;

  if (event.data.target.hp <= 0) {
    await dieCheck(state, event.data.target);
  }
});
```

### content 函数：只写正常操作

content 只写正常操作逻辑，不关心 prevent（由 execute 负责把关）。以后加 prevent 时，content 中的代码无需修改。

### 响应链不需要额外建模

```
executeCard(杀)
  └→ 杀.content
       ├→ choose(目标, 出闪)    ← 栈顶，阻塞等待玩家响应
       │    ├→ 出闪 → executeCard(闪) → 返回，杀被响应
       │    └→ 不/不能出闪 → 返回，进入伤害流程
       └→ damage(目标, 1)       ← 响应链结束，继续执行
```

**响应链天然就是调用栈。** 杀、闪、流离、无懈的嵌套关系，由函数调用自动形成父子关系和时序，不需要额外建模一套响应链系统。
