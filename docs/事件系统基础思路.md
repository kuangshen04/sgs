# 事件系统基础思路

## 核心主张

事件系统不必从零发明，而是**以编程语言的函数调用为基础，在上面加一层事件语义**。

### 从函数继承的基础设施

因为事件系统构建在函数之上，天然具备：

- **父子关系** — 函数 A 调函数 B，B 是 A 的子过程。对应到事件：一个事件的处理中触发了另一个事件，形成树状的事件派生链。
- **调用栈** — 子事件返回后回到父事件继续。天然支持事件嵌套与恢复。
- **时序关系** — 函数调用的先后顺序就是事件的时序。调用顺序即因果顺序。

### 关键前提

**单线程。** 一般游戏规则是线性、顺序执行的，同一时刻只有一条结算路径在跑。不存在两条规则并发竞争的问题。这极大降低了事件系统的复杂度——不需要锁、不需要事务、不需要考虑竞态。

这条前提成立才是合理的，如果后续发现某些场景天然需要并发（比如同时结算多个独立效果），再单独处理，而不是一开始引入并发模型。

## 事件 vs 函数：颗粒度判断

### 判断标准

事件比函数多的就是**状态机 + 可追踪的事件栈**。判定标准是：

> **如果这个流程允许被外部控制/修改（挂载 trigger），就可以作为事件。否则就是函数。**

函数和事件的本质差别不在于"做了什么"，而在于"外部能否干涉它"。

| 事件 | 不是事件（纯函数/内部步骤） |
|------|---------------------------|
| `damage(player, 1)` — 技能可能加伤/减伤/防止 | `calculateBonus(dmg)` — 内部计算，外部无需干涉 |
| `draw(player, 2)` — 技能可能多摸/少摸 | `drawFromPile(player)` — 单张入手的实现细节 |
| `discard(player, cards)` — 技能可能改弃牌选择 | `moveToDiscardPile(card)` — 牌移动的实现 |
| `useCard(card, targets)` — 技能可能改目标/阻止出牌 | `filterTargets(card)` — 合法性校验封装 |

### 用 prevent 检验颗粒度

**"能 prevent 的最小有意义单位"就是事件的合理颗粒度。**

```
❌ moveToDiscardPile(card).prevent()
   → 太细，防止一张牌移动到弃牌堆没有独立意义

✅ discard(player, cards).prevent()
   → 刚好，"这次弃牌不发生"是一个完整的有意义的干预
```

事件粒度有自然的层级关系：

```
useCard（事件本身）
  ├→ chooseTargets（可能是子事件）
  ├→ payCost（可能是子事件）
  └→ resolveEffect（可能是子事件）
```

`useCard` 整体可以被 prevent（"不许出这张牌"），同时内部某些步骤也可以被各自 prevent（"不许选这个目标"）。

## 输入与输出

事件以函数为蓝本，自然也有输入和输出。

```
await damage(player, 1)
```

- **输入**是调用方的**意图**（对 player 造成 1 点伤害）
- **输出**不应是裸数值（如 `2`），而应是**事件结果收据**——一个记录了"意图经过技能链修改后实际发生了什么"的结构化对象

```js
const result = await damage(player, 1)
// result ≈ {
//   success: true,          // 伤害是否实际造成
//   actualAmount: 2,        // 经技能修改后的实际值
//   target: player,         // 最终目标（可能被转移）
//   cause: 'damage',        // 事件类型
//   record: [...],          // 修改记录链
// }
```

输出是结构化收据而非裸数值，原因有三：

1. **调用方需要知道细节**来决定后续行为
2. **链式反应需要上下文**——后续技能要追溯伤害来源、实际值等
3. **调试与回放**——有了收据就能重现"什么意图经过什么修改变成了什么结果"

## 发布订阅（Trigger）系统

大体上是最常见的发布订阅模式，但有**两个额外的限制条件**。

### 限制一：触发顺序由规则集规定

触发系统自身不做排序决策，只提供一个**排序接口**让上层的规则引擎注入顺序策略：

```
triggerSystem.on('damage.before', skillA)
triggerSystem.on('damage.before', skillB)
// 顺序由规则引擎决定：座位逆时针 / 当前回合角色优先 / ...
```

触发系统保持**顺序无关**，承诺"按你给的顺序执行"即可。

### 限制二：订阅者和事件互动

订阅者不是"收到通知然后干自己的事"，而是**伸手进事件内部修改它**。

## 事件对象 = 状态机 + 交互协议

事件对象在触发链中传递，由三部分组成：

- **数据部分**：事件当前的参数状态（伤害值、目标、来源……）
- **协议部分**：prevent / modify / transfer / isPrevented 等固定接口
- **不可变性约束**：订阅者不能随意改数据，只能通过协议操作——让事件的变化可追溯

三者合在一起形成一个轻量状态机（仅指"有一个地方存状态+规定如何交互"，与马尔可夫过程或事件阶段的提法无关）。

### 交互协议

```js
event {
  data: { target, amount, source, ... },

  // 固定交互协议（不是随意暴露 data 字段）
  prevent(): void,              // 防止此事件
  modify(changes): void,        // 修改事件参数
  transfer(newTarget): void,    // 转移目标
  isPrevented(): boolean,       // 查询当前状态

  // 订阅者不能直接操作：
  // ❌ event.data.amount = 999  —— 不允许随意篡改
  // ✅ event.modify({ amount: 999 }) —— 通过协议，可追踪
}
```

### 事件结果 = 最终快照

```
await eventObject      ← 创建事件对象，送入触发链
     ↓
[技能链拦截修改]        ← 各订阅者通过协议修改事件对象
     ↓
return eventObject     ← 返回触发链走完后的最终快照
```

## 事件执行骨架

### executeEvent

几乎所有游戏动作都遵循三段式结构：

```
before（技能拦截/修改意图）→ 核心操作（原子行为）→ after（技能响应结果）
```

damage、recover、draw、discard、judge……都是如此。因此抽象出一个通用骨架：

```js
async function executeEvent(type, event, coreAction) {
  await triggerSystem.trigger(`${type}.before`, event)
  await coreAction(event)
  await triggerSystem.trigger(`${type}.after`, event)

  return event
}
```

### content 函数：只写正常操作

```js
// content 只写正常操作逻辑，不关心 prevent
async content(event) {
  event.target.hp -= event.amount
}

// 调用方：
const result = await executeEvent('damage', event, content)
```

## 玩家交互

### choose 原语

基础 API 很简单：

```js
const result = await choose(player, whatToChoose)
// whatToChoose 描述"需要选什么"（出闪、选目标、选花色……）
// result 是玩家的选择结果
```

**`choose` 本身可以是一个事件**，这样技能可以在"让玩家选什么"的时候介入修改选项——以后如果需要可以展开。

### 出牌和杀闪的实际流程

```js
// 出牌
async content(event) {
  const result = await choose(event.player, 出牌规则)
  if (result) {
    await executeCard(result)
  }
}

// 杀
async content(event) {
  const result = await choose(event.target, 出闪)
  if (result) {
    // 被闪响应了，无事发生
  } else {
    // 没闪，造成伤害
  }
}
```

### 核心结论：响应链不需要额外建模

```
executeCard(杀)
  └→ 杀.content
       ├→ choose(目标, 出闪)    ← 栈顶，阻塞等待玩家响应
       │    ├→ 出闪 → executeCard(闪) → 返回，杀被响应
       │    └→ 不/不能出闪 → 返回，进入伤害流程
       └→ damage(目标, 1)       ← 响应链结束，继续执行
```

**响应链天然就是调用栈。** 杀、闪、流离、无懈的嵌套关系，由函数调用自动形成父子关系和时序，不需要额外建模一套响应链系统。

## 事件栈查询：getParent

### 问题

古锭刀挂载在 `damage.before`，但它的逻辑需要知道"这个 damage 是否由杀命中触发"。caller（杀）无法预知未来所有技能的需求，不可能提前塞足字段。而裸读父事件又太危险。

### 折中方案：按事件名向上查询

```js
// 古锭刀在 damage.before 中的写法
const useCard = event.getParent('useCard')
if (useCard?.card.name === '杀' && event.target.hand.length === 0) {
  event.modify({ amount: event.amount + 1 })
}
```

含义：**从当前事件栈向上查找最近一个名为 `useCard` 的父事件**。

### 为什么好

**有契约。** 事件名决定了数据签名——`getParent('useCard')` 的返回值结构是已知的，不依赖调用栈细节。

**深度弹性。** 不关心中间隔了几层（是否经过流离、反馈等中间事件），只关心"最近的那个 useCard 是谁"。

```
executeCard(杀)
  └→ executeCard(流离)           ← 多了一层
       └→ damage.before
            └→ 古锭刀.getParent('useCard')
            // 正确返回"杀"的 useCard 事件
```

如果两个 useCard 嵌套（比如流离本身也是 useCard），取最近的一个 → 返回流离，古锭刀自然不该触发，正确。

**null 是安全状态。** 如果 damage 是由技能效果触发而非杀，`getParent('useCard')` 返回 null，技能优雅地什么都不做，不需要调用方做任何事。

### 与 cause 字段的关系

两者不是非此即彼：

| 方案 | 适合的场景 |
|------|-----------|
| `event.cause`（事件自带） | 高频、确定的因果信息，如"damage 是由 card 还是 skill 出发的" |
| `event.getParent(name)`（按需查询） | 低频、特定技能的上下文需求，避免所有事件都预塞无用字段 |

可以共存。基础事件携带最常用的因果元信息，特殊需求用 getParent 补充。

### 风险意识

隐式数据流——读代码时看到 getParent，需要知道"这里依赖调用上下文，只有在这个事件是某个父事件的子事件时才生效"。这是可接受的代价：签名约束（事件名=已知结构）+ null 安全（查询不到不报错），已经把这个风险控制在了"代码可读性"层面，而不是"运行时崩了"的层面。
