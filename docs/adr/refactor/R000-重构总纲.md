# R000 MVP 粗模块与不兼容重构

- **状态**：边界已定；迁移待做（见 `../../TODO.md`）
- **目标落地位置**：迁移期 `src/mvp/`；切换后提升为 `src/` 的一级模块

## 背景与现状实测

现实现功能完整，但 `Game` 容器、`types.ts`、事件字典、`flow/gameFlow.ts` 与规则集同时横跨多个
业务簇；继续在原目录内逐文件搬家，会迫使新边界长期兼容旧接口。当前基线仅作为旧实现快照：

| 事实 | 核对 |
|---|---|
| 编译干净 | `pnpm exec tsc --noEmit` → 通过 |
| 旧测试全绿 | `pnpm exec vitest run` → 54 files / 488 tests 通过 |
| `Game` 同时持有规则集、事件、位置、UC 等状态 | `src/game.ts` 的 `Game` 接口 |
| `gameFlow.ts` 同时实现 game / round / turn 与具体阶段 | `src/flow/gameFlow.ts` |
| `types.ts` 反向引用位置与效果模块 | `grep '^import' src/types.ts` |

这次目标不是保持全部标包行为，而是先用最小可运行模型建立正确的粗模块边界。旧实现尚未迁移的
内容允许暂时删除、移出编译范围或保留为只读参考，不建设兼容壳。

## 决策

### 1. 先划粗模块，不预拆内部形态

第一轮模块如下；在出现 2–3 个真实用例前，不拆 definition / runtime / manager：

```text
地基：Event、Selection
基础载体：Card/CardArea、UsedCard/UsedCardArea、Player、Seating
规则能力：Effect、Skill、HP、Life
流程骨架：GameFlow、Round、Turn
业务流程：UseCard、PlayPhase、DiscardPhase
联结模块：按真实跨模块规则建立（首例为 UC—Effect）
```

接口、事件数据与公开原语跟随所属模块，不再建立通用 `types.ts`、业务事件总字典或公共契约层。

### 2. 依赖边使用【外】/【里】描述

`A → B` 表示 A 依赖 B 的公开接口；【外】/【里】描述控制流形态，不改变静态依赖方向。

- **【外】**：上层在下层能力外组织主流程；上层掌握调用顺序与业务语义。
- **【里】生命周期同步型**：状态随下层实例同生共灭，但主要行为仍由上层在外组织。
  状态可直接附着，也可由 manager + map 保存；实现位置不改变模块所有权。例：HP → Player
  （状态【里】，行为【外】）。
- **【里】流程注入型**：上层把 hook / guard / provider / strategy 注册进下层流程，主流程在下层，
  运行时由下层回调上层贡献。例：UC → moveCard（离区反作用【里】）、TriggeredEffect → Event
  （hook【里】）。

守卫、贡献和钩子只是流程注入型的具体协议，不再细分成模块关系类别。

### 3. 两个可独立模块的联动由第三个模块拥有

当 A、B 都允许脱离对方存在，而一条规则必须同时理解二者时，建立联结模块 C：

```text
A ← C → B
```

C 对两边的每条边仍分别标注【外】或【里】；A、B 不互相 import。联结模块按具体规则命名，
不建设万能 `integration/common` 层。只做启动期注册的是 assembly；拥有运行期联动语义的才是联结模块。

首个明确用例是 UC—Effect：UC 可以没有效果，Effect 也可来自技能或裸效果；装备 UC 当前是否授予
某效果由联结模块表达。现有 `EffectCommon.equipType` / `effectOwnedBy` 反查 UC 的职责在迁移时移出 Effect。

### 4. 各粗模块的边界

- **Event**：只管 scope、父子栈、历史和 hook 机制；具体事件词汇属于产生它的业务模块。具体设计见 R001。
- **Selection**：只管 frame / answerKey / plan / session 与 Controller 交互；不认识牌、角色和规则。
  使用业务词汇和约束的选择工厂随业务模块走，在外生成逐次 Frame。可选边界、回溯边界、AI 意图及
  Session 的执行前边界见 R003。
- **Card/CardArea**：没有效果的物理对象、区域和移动；`moveCard` 是 Card 模块自己的事件流程。
- **UsedCard/UsedCardArea**：正在发挥作用的牌载体；在外使用实体牌字段和移动能力，并向实体牌移动
  注入完整性反作用。Card 不认识 UC。
- **Player**：局内稳定身份与最小生命周期载体，不吸收座次、HP、技能、区域等模块的状态或行为；
  外置状态、未来 Seating 与只读调试联结边界见 R004。
- **Seating**：运行时是按逆时针顺序保存的逐局 Player 数组，座位号为 1-based；不读取死亡状态，
  Distance 以后同时依赖 Seating + Life 计算有效座次差。具体设计见 R005。
- **Effect**：先统一归属/有效性/生命周期语义，提供主动、触发、持续三种消费协议；不强求三者共享
  同一个执行方法。主动效果由选择包装器在外收集；触发效果注册进 Event；持续效果贡献 getter 链。
- **Skill**：在外控制 Effect 生命周期；storage 与 Skill/Player 生命周期同步【里】。
- **HP / Life**：状态随 Player 生命周期【里】，行为在外；HP 在外调用生死检查。未设计的濒死救援
  不为旧行为预留兼容接口。
- **GameFlow / Round / Turn**：纯时间骨架，除彼此的流程组合关系外只依赖 Event；参与者、终止条件和
  phase plan 由外部给入。实际阶段注册到 Turn 的显式槽位【里】，阶段顺序不得依赖注册顺序。
- **UseCard**：包在 UC 外，依赖 UC、目标 Player 与 Event，全部【外】；接受已经决定好的牌和目标，
  不依赖 Selection、Effect、显示层或全局 RuleSet。

### 5. 不兼容迁移与质量闸

- 新实现先放在临时 `src/mvp/`，并使用独立的 `tsconfig.mvp.json`、单测命令和 E2E 入口；
- 新实现不得 import 旧 `game.ts`、`types.ts`、`rules/`、旧 content 或旧测试辅助；
- 旧 488 个测试只证明重构前基线，不是迁移期验收项；不迁移的模块和测试可删除或移出默认发现范围；
- 迁移期必须保持 **MVP 自身**编译、模块单测和 E2E 全绿；切换后默认 `test` / `start` / 编译命令
  指向新实现，不长期保留一个默认失败的项目；
- MVP 跑通后把 `src/mvp/*` 提升到 `src/*`，删除旧实现和临时迁移根，不保留 v1/v2 兼容入口。

### 6. 本阶段不设计 DI 框架

模块先通过显式参数、hook 注册与具体联结模块表达依赖，不建立 Service Locator 或通用模块容器。
边界稳定后，DI 只负责把已有替换接缝装配起来，而不是再次定义模块边界。原 ADR-0009 的容器形状
不预设为新 DI 的最终形状。

## MVP 验收边界

MVP E2E 至少跑通：显式装配两名角色 → Turn 的注入阶段 → scripted Selection 选择牌与目标 →
UseCard 创建并结算 UC → 目标 HP 变化与死亡 → 注入的终止判断结束 GameFlow → 实体牌正确进入弃牌区，
同时验证事件父子关系。主动/触发/持续效果、Skill storage、UC—Effect 联结与阶段显式顺序分别由
模块单测覆盖。

响应、判定、距离、完整装备内容、标包武将、完整 AI、回放与插件 DI 不属于本轮验收。
