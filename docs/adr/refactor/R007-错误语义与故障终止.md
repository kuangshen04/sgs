# R007 错误语义：规则结果显式、内部故障终止本局

- **状态**：边界已定；所有后续模块必须遵守
- **落地位置**：横切规则；Event / Selection / Card / Match Assembly 及后续业务模块

## 背景

三国杀结算是一条有因果顺序的状态变化链。若规则定义、模块不变量或 hook 执行发生未知异常，当前内存
状态和后续规则语义已经不再可信；捕获异常后继续结算只会把首个错误扩散成更难定位的错误。另一方面，
“不能使用”“玩家放弃”“效果被取消”“游戏结束”等都是正常规则分支，不应滥用异常表达。

因此新规则引擎采用 fail-fast / fail-stop：内部故障完成必要安全解卷后向 Match 边界传播并终止本局，
不建设未知异常后的局内恢复、通用事务回滚或继续运行机制。

## 决策

### 1. 正常规则结果不是 Error

以下情况使用查询、判别联合、状态字段或流程返回值表达：

- 当前不能使用某张牌、目标不合法；
- 玩家不发动技能、响应窗口放弃；
- 目标或效果被取消、抵消、无效；
- 跳过阶段、循环正常结束；
- 胜负条件满足、游戏正常结束。

```ts
canUse(...): boolean;
legalTargets(...): readonly Player[];

type Response =
  | { readonly type: 'play'; readonly card: UsedCard }
  | { readonly type: 'pass' };
```

新实现不使用 `GameOverError`、`SkipPhaseError`、`CancelTargetError` 等异常模拟正常控制流。旧 ADR 中的
`GameOverError` 只描述旧实现，不构成 R000 重构目标。

### 2. 外部非法输入在 Controller / adapter 边界拒绝

真人前端提交不存在的 OptionId、过期回答或格式错误时，只要 Session 尚未修改，就由 Frontend
Controller 拒绝并要求重新提交。超时、断线和托管由 Controller adapter 处理，不进入规则引擎的未知
异常恢复。

AI 或 scripted Controller 产生非法命令通常表示程序或测试错误，应直接抛错。若外部传输本身失败且
没有明确暂停/托管策略，则由 Match 应用边界终止本局，规则代码不得静默选择默认答案继续。

### 3. 未定义调用和不变量破坏直接抛错

下列情况属于内部故障：

- 同一 Card 同时位于两个 Area，Area 内容与位置索引不一致；
- UC 材料冲突、实例重复提交、规则定义缺失；
- 对执行入口传入已死亡目标等未定义参数；
- Event 栈纪律、DI 依赖图或模块注册不变量被破坏；
- content、hook、Controller 或外部模块抛出未知异常。

严格命令在前置条件不满足时直接抛错，不返回 `null`、`false` 或“尽量继续”。调用方不得捕获未知异常
后进入下一结算步骤。

### 4. 允许部分成功必须是公开业务语义

默认修改命令采用严格输入；只有模块文档明确声明时才能返回部分结果。例如 R006 的 `moveCards` 明确
允许跳过当前无位置或在 before 期间已被移动的牌，并返回实际 moved 列表。不能把这种行为推广成所有
命令的通用容错方式。

正常规则拒绝与严格命令错误的判据是：

```text
调用前用于生成选择的规则查询 → 正常结果
确认执行后违反执行域或模块不变量 → 内部故障
文档显式规定的竞争/部分成功 → 已定义结果
```

### 5. 安全解卷不等于恢复游戏

Event、原子状态操作和装配入口仍必须使用 `finally` 或等价协议维护基础结构：

- Event 无论正常或异常都定稿 endId、恢复严格栈并执行 clear；
- Card 的 leave hook 抛错后仍完成当前牌的目标进入，再传播异常；
- 已登记的外部监听、网络连接、计时器等在 Match 结束时释放；
- 故障快照和日志应尽量在可检查的一致状态上产生。

这些收尾只用于阻止故障污染进程和调试信息，不授权继续当前对局。content 抛错时 Event.after 不运行，
异常在清理后继续向上传播。

### 6. Match 是唯一未知故障边界

未来 Match Assembly 在最外层捕获未知异常：

```ts
try {
  return await runGameFlow(...);
} catch (error) {
  await recordFault({ error, eventHistory, randomSeed, debugSnapshot });
  throw error;
} finally {
  await closeExternalResources();
}
```

Match 边界可以标记本局 faulted、记录 Event 历史、RNG seed 和只读调试快照，并通知应用层异常终止；
不得吞掉错误后重新进入 GameFlow。规则模块内部不各自建设“错误恢复器”。

### 7. 不建设通用回滚

一次规则行为可能已经创建子事件、移动其它牌、消耗随机数、改变 Controller 状态或向外发送信息；只
回滚几个对象或 Map 无法恢复完整因果。因此未知异常后不尝试回到事件前继续运行。

未来若需要生产容灾，方向是确定性日志、RNG seed、可信快照和从边界重建/重放；这是应用和回放层能力，
不改变规则引擎 fail-stop 语义。

### 8. 模块 API 约定

| API 类别 | 约定 |
|---|---|
| 规则查询 | 返回 boolean、候选集或明确状态，不抛出“规则不允许”异常 |
| 外部输入解析 | 修改状态前校验；可拒绝并重试 |
| 严格状态命令 | 前置条件或不变量失败直接抛错 |
| 显式部分成功命令 | 只按所属模块 ADR 返回实际结果 |
| content / hook | 未知异常向上传播，不捕获后继续 |
| clear / finally | 必须运行必要结构收尾，但不改变故障结论 |

内部错误第一版可以使用带上下文和 `cause` 的普通 Error；只有外部调用方确实需要按类别处理时，才增加
专用错误类型。禁止为了“完整”给每个内部命令建立 `Result<Success, InternalError>` 联合。

## 测试与验收

- 严格命令的非法前置条件应断言抛错且不静默修改其它状态；
- content / hook 异常后 Event 栈和 clear 必须正确；
- 异常后的基础对账快照应尽量可读，但测试不得继续执行业务结算来证明“还能玩”；
- 正常取消、放弃、游戏结束等路径必须用普通结果测试，不依赖异常类型；
- Match 落地后补“内部故障 → faulted → 记录诊断 → 不再接受命令”的纵向测试。

## 与其它决策的关系

- 延续 R001 的异常传播和 Event finally 解卷语义；
- 延续 R003 的非法 Selection 命令不修改 Session，真人输入重试由 Frontend Controller 负责；
- 延续 R006 的严格 atomicCardMove、显式 moveCards 部分成功和 hook 异常守恒；
- 取代旧 ADR-0001 / 0008 中把 `GameOverError` 当正常整局控制流的目标方案；
- Match / DI 检查点必须实现本篇的单一故障边界，但不得把 Match 变成 Service Locator。
