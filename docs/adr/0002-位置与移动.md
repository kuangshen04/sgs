# ADR-0002 位置与移动：CardArea / 集中索引 / 移动原语 / 对账

状态：已落地（阶段 2；驻留区守卫与内部通道于阶段 3-R1 补入）
落地位置：`src/position/cardArea.ts`、`move.ts`、`cardActions.ts`、`cardAreaCheck.ts`

## 背景与问题

"牌在哪"必须只有一个答案，且必须能被移动流程、历史、回放一致地查询。参照无名杀
（区域是 DOM nodelist、位置靠遍历）与 FreeKill（`card_place` 集中索引）的经验，选后者：
**容器是数组权威，索引是派生态**。

## 决策

1. **位置模型**：`CardLocation = {player, zone:'hand'|'equipment'|'judgment'} | {zone:'deck'|'discardPile'|'processing'}`。
   牌堆顶/底**不是位置**，是取放策略（收敛进 `putTop`/`putBottom`）。
2. **容器 = 受控 `CardArea`**：对外只有 `cards` 只读视图与受控写方法
   （`add`/`addAll`/`insertAt`/`removeById`/`removeLast`/`removeFirst`/`clear`/`replaceAll`）；
   没有数组方法、没有 `length`、不实现迭代器——避免"像数组一样被随手改"。
   装备区不是列表（`PlayerEquipment` 四槽位对象），槽位由 UC 位置决定（见 ADR-0003）。
3. **`game.cardIndex: Map<cardId, CardLocation>` 是派生态**：只由容器方法与装备槽位写点维护；
   不参与序列化，加载时重建。`getCardArea(game, card)` 是唯一的位置查询入口。
4. **移动只有两个入口**（`move.ts` / `cardActions.ts`）：
   - **公开 `moveCards({cards, to, reason, mover})`**：来源由索引对每张牌派生；不在任何位置的牌自动跳过
     （部分成功语义）；空移动不发事件；**装备槽 / 判定区终点硬报错**（驻留区只能经 UC 层进入，见 ADR-0003）；
   - **内部 `movePhysical(spec)`**：无守卫的低层原语，含 `atBottom`（牌堆底）、`equipSlot`（装备槽）、
     以及"取出 → 若来源是驻留区则发 UC 层钩子 → 放入"的唯一物理写点。UC 层与牌堆策略用它。
5. **移动都有语义标签** `CardMoveReason`（draw/judge/discard/play/use/equip/replace/give/obtain/transfer/
   resolve/reveal/reshuffle/virtualBroken），`CardMove` 事件带 `cards`/`fromAreas`/`to`/`reason`/`mover`，
   "本回合失去过牌"这类查询走历史 + reason 过滤。
6. **对账不变量（`verifyCardState`/`assertCardState`）**：一牌一位置 + id 唯一（物理容器 ↔ 索引双向核对）
   + UC 绑定核对（见 ADR-0003）。它只校验不变量，不做"牌总数守恒"（牌可能被移出游戏，本引擎暂无 void）。
   测试/调试期作为 sanity net 使用。

## 影响与后果

- 位置查询 O(1)；容器写入集中，步进式重构（阶段 2）后规则代码不再直接碰容器数组。
- `moveCards` 的"部分成功"语义意味着调用方**没有**"牌一定动了"的保证，需自行判定（现有调用点都如此）。
- 装备区与判定区在物理层是两种容器（对象 vs 列表），UC 层统一成了"驻留区"（ADR-0003）。

## 不采纳 / 延后

- **void/移出游戏 zone**：等真实用例（`CardLocation` 加一个 union 分支即可）。
- **CardArea 内部结构自定义**（子类/注入：牌堆顶底、装备区、判定区顺序）：触发条件与登记处见
  `../TODO.md`（"伴生事项"）。
- 区域进入/离开的**通用**钩子抽象：目前只有"离开驻留区"这一个钩子（UC 层需要），等第二、三处需要再抽象。
