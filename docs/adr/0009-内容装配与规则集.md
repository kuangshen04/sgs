# ADR-0009 内容装配与规则集：容器 / 规则集 / 显式装配

- **状态**：已落地
- **落地位置**：`src/rules/`（`ruleSet.ts` / `cardDef.ts` / `cardFace.ts` / `random.ts`）、
  `src/content/standardPack.ts`、`createGame(..., { ruleSet })`

## 背景：定义层原先活得太久

卡牌/技能/武将定义原先放在**模块级单例注册表**（`content/cardRegistry.ts`、
`heroRegistry.ts`、`effects.ts` 里的 `_skills`）里，靠 `import './cards/index.js'`
这类**副作用**注册。后果：

- 注册表活到进程结束、且跨局共享——"这局装了哪些内容"是不可见的运行时事实；
- 测试借真内容造场景（判定阶段的测试必须用乐不思蜀/闪电），下层测试驱动上层模块
  （`content/*.test.ts` 里 `import { useCard }`）；
- 引擎为了做显示/洗牌/身份推导，被迫 import `content/`（看着像依赖倒置，实为引擎件住错了地方）。

## 决策

1. **两层分开，生命周期不与 game 绑定**：
   - **容器 Container** = 装配期入口（`cards/skills/heroes` 的 register、`useInfo`、`addSetupHook`），
     **谁造谁释放**；一套内容服务很多局，测试可以每个用例造一个只装了它需要的卡牌的容器。
   - **规则集 RuleSet** = 运行期**只读窄接口**（`cards/skills/heroes` 的查询 + `setupHooks`），
     交给 `createGame` 后由 `game.ruleSet` 引用。**game 只持引用**：不构造、不释放，也不提供
     "按名字查服务"的动态查找。
2. **装配必须显式**：`installStandardPack(container)` 是"标包装了哪些内容"的唯一可见事实；
   `content/` 下没有任何副作用 import；`createGame` 的 `ruleSet` 是**必填**项
   （不做隐式默认装配——留默认就等于把单例改个名字）。
3. **引擎件搬出 content**（原先住在 `content/cardRegistry.ts`，是"引擎 import content"里的大多数）：
   定义契约 `rules/cardDef.ts`；牌面与显示 `rules/cardFace.ts`（`asUsedCard`/`cardEmoji`/
   `displayNumber`/`cardFaceText`）；随机源 `rules/random.ts`（洗牌，**rng 服务的注入点**，
   种子化与回放见 `../TODO.md` 阶段 6）。
   注：这三个文件当时被一起放进 `rules/` 只是为了"离开 content"，它们与注册面**不是同一层**
   （`asUsedCard` 属 UC 簇、显示件属显示簇、`shuffle` 属随机源）；归位见 ADR-0010 的迁移项 a。
4. **效果查询面属于规则书**：`allEffects/triggeredAt/persistentOf/responsesFor/conversions/
   activated/timings` 变成 `game.ruleSet.skills.*`；`defineSkill` 退化为**纯构造**，
   同名查重与规则文本回填发生在 `register()`（info 数据源由内容包在装配期用 `useInfo` 提供，
   于是 `effects/` 不再认识 `docs/*.json`）。
   注：`Skill`/`Effect`/`defineSkill` **留在 `effects/`**——定义与实现同住（ADR-0004/0010），
   因此 `ruleSet.ts` 依赖 `effects/` 是合法边，注册表的元素类型本就来自那里。
5. **内容 → 引擎的钩子 = `setupHooks`**：无懈可击的响应窗口由内容在装配期挂上
   （`c.addSetupHook(installWuxieTrigger)`），引擎的触发分发不再认识任何具体卡牌。
6. **裸效果与技能效果同一份效果集合**，注册面分别对应
   `skills.register` 与 `skills.registerBareEffect`。

### 当前取舍（DI 落地后预计调整）

`game` 持有规则集引用是**当前实现选择，不是不变量**：将来做完整 DI（`../TODO.md` 阶段 5）时，
服务（decision / rng / victory）在装配期解析后交给 game，`game` 依旧不持有容器。
`context` 式贯穿参数暂不改名——它换不来语义收益，只换来几百处调用点改写。
**DI 能换的是服务，不是内容**（技能定义即实现，ADR-0010 第 5 条）：所以本文的容器是**装配面**，
不是"实现替换接缝"。

## 代价与已知约束

- **装配顺序有意义**：几处 AI 优先级在装配期读别的牌定义（如丈八蛇矛读【杀】的 `usePriority`），
  故 `standardPack` 按 基本牌 → 锦囊 → 延时 → 装备 → 武将 的顺序装配；换包时同样要满足。
- **`CardType` 仍是闭合枚举**：测试内容只能借现有槽位承载自己的定义，内容包要**新增**卡牌身份
  需先扩展 CardType（记在 `../TODO.md` 阶段 4）。
- **测试分层**（见 `../代码结构.md` 测试约定）：下层模块的单元测试用 `testGame/testContainer`
  现场注册测试内容；"内容 × 流程"的集成测试单独标注（如 `flow/gameFlow.test.ts` 的
  "judgePhase × 标包延时牌（集成）"）。存量测试一次性迁移**未做**，欠账记在 `../TODO.md`。

## 验收判据（改这块时照此核对）

1. 引擎侧（`events/` `position/` `effects/` `decision/` `flow/` 及各底层助手）没有任何
   "具体内容 import"——只有入口 `index.ts` 与 `test-utils.ts` 认识 `content/`；
2. `src/content/**` 无副作用 import，且不反向依赖上层模块；
3. 有测试证明**不加载标包**也能跑通判定阶段与触发分发（`flow/judgePhase.test.ts`）；
4. `createGame` 不传 `ruleSet` 编译不过；
5. 标包内容齐备的断言写在 `content/standardPack.test.ts`（装配结果，而非某个全局注册表）。
