# ADR-0010 模块分层与依赖方向：接口随模块 / 命名表与机制分家

- **状态**：判据已生效；迁移项 b 已落地，a/c 待做（见 ../TODO.md）
- **落地位置**：全部 `src/`；本文只定判据与目标分层，不含新代码

## 背景与问题

`types.ts`（Card / Player / GameState / HeroDef / CardType…）与 `events/types.ts`（引用各簇词汇的
事件数据表）这类"什么都有"的类型文件，会制造一个错觉：**应该有一个通用契约层**，所有模块都依赖它。

这个错觉有两处代价：

1. 把接口从它所属的模块里挖走——而**定义与实现常常不可分**（ADR-0004：技能 = 元数据 + 效果集合，
   效果函数就是技能本身），挖出来的"契约"没有独立意义；
2. 让"契约层"变成人人都能看到的公共池，**依赖方向反而不可见**——谁真正需要谁，从签名里消失了。

三条实测事实（可以复现，判据由此而来）：

| 事实 | 核对 |
|---|---|
| **事件机制自足**：`GameEvent.ts` / `TriggerSystem.ts` / `history.ts` 只 import `Game`（类型）与彼此，不 import 事件类型表 | `grep "from './types.js'" src/events/{GameEvent,TriggerSystem,history}.ts` → 0 |
| **决策本体自足**：`decision/selection.ts` 只 import `Game`（类型）+ `Player` | `grep '^import' src/decision/selection.ts` → 2 行 |
| **effect ↔ skill 只有一个耦合点**：`EffectCommon.skill` / `equipType` 两个倒查字段 + `effectOwnedBy`/`effectLordGate` 去查技能表；去掉它，`Effect` 就只是"时点 + 条件 + 行为" | `grep 'e.skill\|effect.skill' src/effects/effects.ts` |

## 决策

1. **没有通用契约层；接口随模块走。** 模块 = 词汇 + 实现 + 它自己的公开接口；跨模块只见彼此的接口。
   `CardDef` 归"卡牌规则查询"簇，`Effect`/`Skill`/`defineSkill` 归 `effects/`（定义与实现同住）。
2. **"命名表"与"机制"必须分开**：
   - **机制**：有行为、有生命周期（`events/` 机制三件套、`position/`、`effects/`、`decision/`、`flow/`）；
   - **命名表**：只有数据形状、没有行为依赖（`types.ts` 的底座词汇与枚举、`events/types.ts` 的事件字典）。
   命名表可以引用任何簇的词汇，但**机制不得 import 事件字典**（事件机制只认"类型名 + 数据 + 栈"）。
   判据：某个 import 只为拿"数据的形状"= 命名表依赖；为了调用行为 = 机制依赖。
3. **依赖边 = 接口边，且接口分层收窄**：每层的接口只引用它下面层的词汇。目标分层：

   ```
   selection   选项 / 步骤 / 会话 / 答案（自足：只需"一个玩家标识"）＝ selection.ts
   ask         询问原语：候选 + 提示 + 默认答案（AI 注入点）→ selection ＝ ask.ts
   events 机制  类型名 + 数据 + 栈（自足）
   position    Card / CardArea / CardLocation / 移动原语 → events
   uc          UC 实例与容器（position 内的第二层，ADR-0003）→ position + events
   rules       规则可选集（canUse / targetFilter / 可放置）→ 规则集 + position ＝ rules.ts
   effects     Effect 五形态 + Skill + defineSkill → selection/ask + uc + position
   windows     动作候选 + 选择计划（只产意图）→ rules + effects + selection/ask
               ＝ useWindow.ts / playChoices.ts / responseChoices.ts
   flow        唯一执行者：用牌 / 响应（含 executeResponse）/ 判定 / 伤害濒死 → 以上
   content     只填定义、只调公开原语
   assembly    容器 / 装配函数 / 建局调用点（唯一同时认识内容与引擎的地方）
   ```

   **关键一条：`selection`/`ask` 在 `effects` 之下，不属于"决策层"。** 触发分发要问"是否发动"（ADR-0005）、
   选择计划要跑会话（ADR-0007）——询问是所有层的公共**机制级服务**，决策层只是它的消费者之一。
   注意 `rules`（规则可选集）与 `ask` 是**兄弟**：都建在 `selection` 之上，`rules` 额外依赖规则集与位置。
4. **内容与引擎不是上下层，而是经接口互相注入**：引擎拿定义契约调用内容的回调
   （`content` / `canUse` / `targetFilter` / `run` / `resolve`），内容拿**公开原语**执行动作
   （用牌、打出、伤害、移动、询问）。两侧都不 import 对方；内容只经"公开原语面"进入引擎。
5. **DI 的含义**：能替换的是**服务**（decision source / rng / victory / 存储），
   不能替换的是**内容及其定义**（技能定义即实现）。因此 ADR-0009 的容器是**装配面**，
   不是"实现替换接缝"——接缝在服务面（`../TODO.md` 阶段 5/6）。

### 四条红线

1. 引擎侧不得 import `content/`（ADR-0009 判据 1）；
2. **机制不得 import 事件字典**（`events/types.ts`）；字典可以引用各簇词汇，但没人依赖它的行为；
3. **决策不得执行**：`selection`/`ask` 只产出答案；窗口的"动作候选 + 选择计划"属于决策，
   "执行"属于 `flow`（迁移项 b 已落地：响应窗口的 `executeResponse` 在 `flow/respond.ts`）；
4. **询问原语不认识规则**：`ask*` 只吃"候选 + 提示 + 默认答案"，"什么可选"是 `decision.rules` 的事。

## 现状实测（写本文时逐条核对过）

合法且符合本 ADR 的边：

- `position → events`、`uc → position + events`、`effects → uc/position + selection/ask`、
  `decision.rules → effects + uc + position`、`flow → 以上`、
  `content → 公开原语`（`content → flow / position / decision / effects` 的查询面）。

越界边：**0**（迁移项 b 已把响应窗口的执行段移入 `flow/respond.ts`；
`grep "from '../flow/" src/decision` → 0）。

## 不采纳 / 延后

- **集中式契约层**（`contracts/` / `core/`）：见"背景"——它把接口从模块里挖走，代价大于收益。
- **把 `EffectCommon.skill`/`equipType` 改成"注册时带归属谓词"**：唯一能让 effect 完全不认识
  skill/装备的做法，代价是把归属规则从引擎挪到装配点。按本 ADR，技能定义与实现不可分，
  这个需求本身可能不存在——等真有"换实现不换定义"的场景再谈。
- **`context` 式贯穿参数**：见 ADR-0009 的当前取舍（无收益，只换调用点改写）。
- **目录级强制闸**（eslint import 边界 / dependency-cruiser）：现在靠本文 + 人工核对；
  真出现第二次越界再加闸（记 `../TODO.md` 开放问题）。

## 验收判据（新增/改动模块时自查）

1. `grep "from './types.js'" src/events/{GameEvent,TriggerSystem,history}.ts` → 0（机制不依赖字典）；
2. 引擎侧对 `content/` 的具体 import → 0（ADR-0009 判据 1）；
3. `grep "from '../flow/" src/decision` → 0（决策不执行）；
4. `grep "from '../flow/" src/{position,effects}` → 0（下层不依赖流程）；
5. 新模块的接口只引用它下面层的词汇；需要"上面层的东西"时，改写依赖（回调 / 注入），不要 import。
