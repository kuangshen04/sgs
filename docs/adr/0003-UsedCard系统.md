# ADR-0003 UsedCard（UC）系统：两层边界 / 身份 / 规则定义 / 容器 / 生灭

状态：核心已落地（阶段 3 第 4 项 R1–R4、U1–U5）；实体牌 / UC 规则定义边界已定，a4 归位待做
落地位置：`src/position/usedCards.ts`（实例 + 存储）、`usedCardActions.ts`（业务动作 + 钩子）、
`src/rules/cardDef.ts`（UC 规则定义的临时住处）

## 背景与问题

装备效果、延时锦囊、转化牌三件事都需要"**这条牌在规则上是什么**"，而它可能与实体牌不同
（国色：方块牌当【乐不思蜀】；丈八蛇矛：两张手牌当【杀】）。早期实现把这种"身份"作为登记表
挂在物理移动的写点上，于是物理层里长出 UC 业务，而物理牌位置与身份之间没有统一表达——
典型症状：青釭剑与仁王盾的时点冲突、判定区里"哪张牌是乐不思蜀"说不清。

还需区分两个长期被 `CardType` / `CardDef` 的命名掩盖的概念：**实体牌的牌面身份**与
**UC 的规则身份**。普通使用时两者恰好相同，不代表执行语义属于实体牌；转化牌、多牌 UC 与
0 牌 UC 都证明，真正被使用、打出、装备、置入判定区并结算的是 UC。

## 决策

**判据：能承载转化（含 0 牌虚拟）的牌的出现才是 UC。**

- 是 UC：使用（基本/锦囊/装备）、响应窗口的打出、八卦阵的零牌虚拟闪、装备区/判定区驻留；
- 不是 UC：判定牌（含鬼才替换牌）、观星亮出的牌——只是被亮出/摆放的实体牌；
- 手牌/牌堆/弃牌堆里的牌是 UC 的**来源**，本身不是 UC。

**三种对象不可混同**

| 对象 | 拥有什么 | 不拥有什么 |
|---|---|---|
| 实体牌 `Card` | 实体 id、花色、点数、位置；正常使用时的**默认 UC 身份映射** | `canUse` / 目标规则 / 结算内容等执行语义 |
| UC 实例 `UsedCardInstance` | 本次规则身份、实体组成、推导后的牌面、容器位置与局内状态 | 内容定义本身；实例只以稳定身份查规则定义 |
| UC 规则定义（当前名 `CardDef`） | 某种 UC 身份的名称、标签、合法性、目标规则、结算回调及 AI 元数据 | 实体牌的位置与生命周期 |

`CardDef` 因而不是“某张实体牌的定义”，而是**UC 的构造蓝图与规则定义**。当前实现复用
`Card.type` 作为实体牌正常使用时的默认 UC 身份键，复用 `UC.type` 查询 `CardDef`；这是键的复用，
不是把行为挂在实体牌上。a4 收口时可以据此改名和归位，但不得倒回“实体牌拥有执行语义”的模型。

**两层职责**

| | 实体牌层 | UsedCard 层 |
|---|---|---|
| 实体 / 定义 | `Card` + `CardArea`（ADR-0002） | `UsedCardInstance` + UC 规则定义 + UC 容器（装备槽/判定区/处理区） |
| 业务 | 选择实体牌 + `moveCards` + 提供默认 UC 身份 | 构造、合法性、使用/打出 + 长时 UC 的进入/移动/退出 |
| 不含 | 任何 UC 执行语义（只发"离开驻留区"钩子） | 不直接做物理写（经实体牌层内部通道） |

**关键点**

1. **UC 是实体**：`{ id, type, name, suit, number, color, physicalCards, disabled, loc, seq }`。
   自身的 `type/name/suit/number/color` 就是规则身份（"读规则读 UC"）；`loc` 与 `seq` 是**状态**
   （早期"从首张实体牌派生位置"已废弃）。
2. **先构造 UC，再按 UC 读规则**：普通使用由实体牌的默认映射构造同身份 UC；转化技能显式给出
   另一种 UC 身份与实体组成；八卦阵/离间可以构造 0 牌 UC。三条路径构造后完全同形，后续合法性、
   目标与结算只读 UC 及其规则定义，不回到实体牌类型决定行为。
3. **规则身份推导**（`deriveCardFace`，唯一实现）：单牌转化继承该实体牌的花色点数、颜色随花色；
   无牌转化三项皆无；多牌转化无花色点数、全同色才有颜色；**特殊声明逐字段优先**。
4. **四个动作**（`usedCardActions`）：`create`（规则产出，不入容器）/ `enter`（实体牌跟随 + 登记）/
   `move`（UC 迁移）/ `exit`（销毁 + 实体牌去向）；`settle` = "仍在处理区则 exit"，即"清理处理区"。
5. **迁移"先解绑再移动"**：移动途中离开钩子查不到绑定即 no-op，因此物理层**不需要**任何"迁移标记"；
   只有显式 `move` 是迁移（闪电转移、延时牌进出判定区、使用入处理区），其余离区一律**破坏**
   （`onCardLeaveResidentZone`：销毁 UC + 剩余实体牌一次 `virtualBroken` 进弃牌堆）。
6. **约束方向不对称**：装备槽/判定区**双向**（每张实体牌必属一条 UC、每条 UC 的牌必在该区）；
   处理区**单向**（UC 的牌必须在处理区，处理区的牌可以没有 UC）。对账照此执行（ADR-0002）。
7. **选择语义定死**："选择区域内的一张牌" = 选**实体牌**（拆/顺/反馈/流离 cost 等一律如此），
   UC 只作前端提示；纯 UC 的规则自己读 UC（如"判定区同名 UC 只能存在 1 张"由
   `hasJudgmentUsedCardNamed` / `canPlaceDelayOn` 实现）。
8. **装备效果归属经 UC**：`equippedUsedCard(game, player, type)` = 该玩家装备区里**未失效**的那条 UC；
   `disabled` 是 UC 上的失效位（唯一写点 `disableUsedCard`/`restoreUsedCard`）。
   装备效果"实例"就是这条 UC（不另建技能实例），归属每次查询重算 ⇒ 进出/失效/复原即时生效、
   无需 grant/revoke 同步。
9. **0 牌 UC 合法**（八卦阵的虚拟闪、离间的决斗）⇒ 存储主键必须是 `ucId`（不是实体牌 id）。

> **现状差距**：`CardDef` 的名称/目录、`decision/rules.ts` 在构造 UC 前直接查询部分合法性、
> `useCard` 对 `Card | UsedCard` 的兜底物化仍保留旧边界。它们不改变上述语义决定，统一列入
> `../TODO.md` 的 a4 迁移；完成前不得继续扩散“实体牌拥有执行语义”的调用方式。

## 影响与后果

- 判定阶段读 UC（类型/名称/花色），因此国色的"乐不思蜀"在判定区**自动**被识别、被无懈窗口覆盖、
  结算后实体牌进弃牌堆——引擎侧零特判。
- 普通实体牌、单牌/多牌转化与 0 牌虚拟牌只在**构造 UC 的来源**上不同；一旦构造完成，统一按
  `UC.type → UC 规则定义` 执行。实体牌定义/牌堆数据不保管执行回调。
- 装备的进出与失效统一由归属判定表达；青釭剑 = `targeting.after` 失效目标防具 UC +
  `event.onClear` 复原（ADR-0001/0006）。
- 代价：归属查询需要 `game`（UC 表在 `game.usedCards`），由此**规则层查询统一带 `game`**
  （`CardDef.canUse/targetFilter`、`distanceTo/attackRange`、`effectRegistry`）。
- 已声明的行为变化：延时锦囊使用时可被无懈；打出的牌经处理区；多牌源杀被奸雄整条获得；
  仁王盾改为生效阶段无效；闪电转移按规则集（可绕回自己、被抵消仍流向合法下家）。

## 不采纳 / 延后（见 `../TODO.md`）

- **UC 授予技能（grants）**：会让"装备存在"变成两份表示，需在破坏/顶替/死亡/迁移四条路径同步
  grant/revoke，丢掉"归属重算"的免同步性质。升级判据（任一成为真实需求）：装备效果需要"是否发动"
  的询问、`compulsory` 抗性有消费者、需要把装备技能当名字引用/合并（如"视为装备着【八卦阵】"，
  倾向用零牌驻留 UC 表达）。
- **UC storage（木牛流马）**：等第二个用例；届时优先"按需查询"（如 `effectStorage(game, owner, effect)`）
  而不是给所有效果加 shell 参数。
- **迁移时的 grants/storage 重新归属**：同木牛流马。
- **单独的实体牌定义注册表**：当前实体牌除牌面数据、位置与默认 UC 身份外没有第二套行为；另建
  `PhysicalCardDef` 只会复制 UC 定义。等出现只属于实体牌、且不能由牌堆数据表达的真实规则再议。
- 副目标（借刀式）、额外结算次数、加伤/减伤等每目标属性：见 ADR-0006 的"不采纳"。
