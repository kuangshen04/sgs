## 一、内容生态与扩展系统

### 1.1 定位与基本约束（已确认）

- sgs 支持**社区内容**，自定义可以成为玩法的一部分 → 需要模块与插件机制。
- **隔离 = 模块隔离，不做运行时沙箱**：信任社区（无名杀路线的信任前提），
  不采用 JS/Lua 沙箱、受限 DSL 等运行时隔离方案。
- 运行形态：大部分情况**单机**；联机 = **P2P 连房主主机**，服务器（若有）只转发数据、不结算。
  结算只发生在房主端 → 规则引擎保持单机语义，不需要分布式一致性。
- 配套约定：启动插件机制设计时，同步修订 AGENTS.md 的"不提前设计注入接口"一条
  （社区内容即真实消费者，接口设计不再是"提前"）。

### 1.2 两个项目的经验（结论）

- **无名杀之痛**（核心开发者第一手经验）：**隔离性缺失**——API、版本、前后端等各面都没有边界。
  后果：内部 API 被第三方当公共 API 用，核心永远无法自由重构；版本兼容地狱；扩展互相踩。
- **无名杀之资产**：**内置代码编辑器 + 热更新 + 常用技能组合完全不用写代码**。
  新手接触主要玩法的门槛极低——这是无名杀生态能长出来的根本原因。
- **FreeKill 之教训**：控制住了 API 但没有低门槛入口（无内置编辑器，内容要写 Lua），
  社区生态一直起不来。
- 推论：**低门槛的表达面与强隔离的边界必须兼得**，且两者不能走同一条无约束通道
  （无名杀的问题是两者耦合在同一个"随便改全局"的层里；FreeKill 则是把两者一起收紧了）。

### 1.3 插件机制：DI 模块替换（方向，细节重构时定）

核心思想：想改什么就把**整个模块替换掉并重建依赖图**；只要符合接口就改不坏。

参考 DeepSeek Harness（Cordis 模块框架），值得借鉴的 5 件事：

1. **服务即契约**：经容器 key 提供/获取服务，不 import 具体实现——依赖方只见接口。
2. **inject 声明依赖**：加载顺序由"你需要什么服务"表达，而非手动装配序列。
3. **整体替换语义**：替换整个单元，不做字段级 deep-merge；替换后依赖图按服务名重新解析。
4. **可逆注册**：一切副作用注册（监听器、内容登记）带 disposer，卸载/重载可干净撤销
   ——这是热更新的地基。
5. **配置即清单**：条目列表可序列化、可溯源（谁提供谁 / 谁改了谁）、可快照复现；装载失败 fail-loud。

不借鉴（太重）：YAML 表达式引擎、profile/bundle 多层补丁、isolate realm 分组、进程级诊断框架。

sgs 轻量版骨架（示意，非实现设计）：

```ts
// 公共面 = 一组 service 接口（TS 类型即契约）
interface EngineServices {
  rng:      { shuffle<T>(xs: T[]): T[]; seed(n: number): void };  // 换它 → 种子回放
  content:  { heroes: ContentProvider; cards: ContentProvider };  // 内容插件挂这里
  turn:     TurnModule;    // 换它 → 新模式
  respond:  RespondModule; // 换它 → 改响应规则
  life:     LifeModule;    // 换它 → 改伤害/濒死
  victory:  VictoryModule; // 换它 → 身份场/自定义胜负
  decision: DecisionModule;// 换它 → 真人/前端接入
}
// 插件声明：{ provides: 'rng', replace: true, inject: ['content'], apply(ctx) {} }
```

- **两层插件、两种语义，显式区分**：
  - 内容贡献（社区主力：武将/卡牌/技能）→ 挂在 `content` 服务上**增量注册**（append）；
  - 模块替换（机制作者）→ 对整个 service 提供新实现（replace）。
  - 同 service 两个替换 = 装载期显式冲突报错；内容同 id 冲突 = **整单元替换**
    （重定义该武将/卡牌）并记入装载报告——对称地保持"整体替换、不 patch 字段"。
- **容器粒度**（倾向，未定）：应用级一个容器；`Game` 是从容器解析出的局实例
  （事件栈/触发器/玩家状态仍随局隔离，与现状一致）。替换在开局前完成，局内稳定。
- **公共 API = service 接口集**（带 TS 类型）；未声明为 service 的内部函数不可注入
  ——这是对无名杀"内部 API 被当公共 API 用"的直接防御。
- **"可卸载"是模块机制的硬要求**：disposer 齐全才能干净重载，为编辑器/热更新铺路。

### 1.4 降门槛机制（方向，编辑器话题后续另议）

- 表达力分层（L0 免代码数据 / L1 声明式组合 / L2 脚本 / L3 引擎改动）**不是插件机制的主体**，
  而是**降门槛的主要机制**：无名杀式"编辑器 + 热更新 + 免代码组合"是生态生命线。
- 本项目已有地基：`docs/标包*.json` 唯一事实来源（L0 起点）、`effectRegistry` 的 kind 词汇
  （L1 词汇表雏形）、`SelectionOption` 的 label/group/prompt（声明式 UI，插件内容不碰渲染层）。
- 词汇表生长规则（沿用项目原则）：每个词汇有 2–3 个真实用例才进入词汇表，
  且只能由**内建内容提炼**进入——防止插件作者发明引擎无法验证的"伪词汇"。
- 与 DI 的关系：模块可卸载 + 内容可热载 = 编辑器即时生效的技术前提。

### 1.5 回放与联机一致性（方向）

- **对局配置快照**：`{ apiVersion, content: [{id, version}], overrides: {service: pluginId}, seed }`
  序列化 + hash。
- 回放：配置快照 + 事件流即可复现一局（借鉴 DSH 的 snapshot replay 思路）。
- P2P 联机：房主广播配置 hash，不一致即拒绝或同步；结算只在房主端。

### 1.6 开放问题（重构时确认，勿提前定死）

1. 容器粒度：应用级容器 + 每局实例，还是每局全量容器？
2. 第一版 service 切分：候选 rng / content / turn / respond / life / victory / decision；
   切分原则"有真实替换需求才立 service"。
3. replace / extend 双语义与冲突策略的实现细节。
4. DI 化时机：标包收尾后立刻做，还是军争/神话再临作为第一批内容插件接入时顺带做
   （把内容接入当 DI 的第一个真实用例，符合"有例子再抽象"）。
5. 公共 API 的冻结/版本化策略（semver？弃用期？）。
6. 编辑器/热更新的具体承载（web UI？Monaco？与"真人/前端接入"的关系）。

## 二、事件系统：历史 / 因果 / 收尾

> 本节涉及无名杀 `apps/core/noname/library/element/gameEvent.ts` 与
> FreeKill `lua/server/gameevent.lua`、`lua/server/gamelogic.lua` 的事实均已逐源码核对。

### 2.1 两个项目的经验（结论）

**无名杀**：
- **显式历史树**：`parent` + `childEvents[]`（每事件记录全部子事件）+ `next` 兄弟链 + `after` 插队。
  成因：`waitNext`/`insert` 调度把事件树与 JS 调用栈解耦，栈不再是可靠的父记录，被迫显式维护树。
- **无清理钩子**：`finish`/`cancel`/`neutralize`/`untrigger` 终止语义互相纠缠、与技能实现和
  step-dsl 残留耦合；临时状态全靠技能自己记得清理。
- 字段无隔离：`[key: string]: any`，UI 选择状态（filterButton/selectButton/ai…）也挂在事件上。
- 历史：事件 `start()` 时 push 进全局 "everything" 数组；`player.getHistory` 按 `event.player`
  过滤；无 id/end_id。
- 杂项坑：`getParent` 找不到时返回 `{}` 假对象（静默错误源）。

**FreeKill**：
- **DFS 时间戳**：递增 id + 完成时定稿 `end_id`（无子事件则 = id）+ 全局数组哨兵标记子树终点
  + 按类型索引（event_recorder）二分查询。
- **四主流程按事件类型绑定**（prepare/main/clear/exit 四张表，非发布订阅）+ 按实例
  extra_clear/extra_exit；生命周期 ready→running→exiting→dead；`interrupted`/`killed` 双标志。
- **clear 走独立不可中断的 ClearEvent**：先 clear + extra_clear → 再定稿 end_id → 最后出栈；
  exit 在主协程 main 正常返回后执行，被 `__breakEvent` 打断时协程被 close、exit 不跑、clear 必跑
  （两阶段是协程语义逼出来的）。
- 中断：`breakEvent` 让出 "__breakEvent"，调度器把栈上到目标事件全部标 `killed`，之后按栈序自动清理。
- 查询：searchEvents / getEventsOfScope（Game/Round/Turn/Phase 边界）/ getEventsByRule /
  findParent（含继承匹配）；`specific_events_id`（Damage 单独编号，支撑"第 N 次伤害"）。

### 2.2 历史存储模型（已确认）

**决策：DFS 时间戳法（FreeKill 式），不构建显式历史树。**

取舍理由：
1. **查询形态匹配**：三杀技能的历史需求几乎全是"范围 + 类型 + 谓词"（无双/裸衣/克己/奸雄），
   正是区间查询的甜点；"枚举全部子事件"这类纯结构查询在引擎内直接有调用栈，不需要查历史。
2. **正确性前提免费满足**：时间戳法要求执行严格栈纪律——正是本项目"事件即函数调用"的核心主张；
   `GameEvent.execute` 已有"构造与执行必须同上下文"的运行时校验。
3. **扁平数组 = 回放流**：append-only、可直接序列化；无名杀的树是可变图
   （next/after/联机 `_modparent` 改写父指针），忠实回放还要先拍平。
4. **中断下仍闭合**：被打断的子树照样定稿 end_id，历史里依然是合法闭区间；
   我们的 finally 使 end_id 定稿只有唯一退出点，结构性保证不漏。
5. **成本最低**：一个计数器 + 一个数组；无名杀选树是被调度解耦逼出来的，我们没有那个因。

**红线**：一旦引入"延迟执行/插队"的真实用例（破坏 DFS 序），必须先回头补显式树——
在此之前时间戳法会静默失效。写死这条，防止在不理解前提的情况下引入调度解耦。

**保留 parent 链**：`getParent`（因果/边界定位）继续可用；时间戳数组是历史查询的权威存储，
两者并存、分工不同。

**历史全量保留**（不做活窗口裁剪）：不仅有本回合计数技能，本轮、本局游戏计数技能很快会出现。

落地要点（方向）：
- `history: GameEvent[]` + 全局计数器；push 赋 id，finally 定稿 end_id（无子事件则 = id）。
- 按类型索引 `Map<type, ids[]>` 先不做、线性扫描；性能议题（第五节）再评估二分。
- FreeKill 的哨兵条目仅在"从数组还原树、不持有事件对象"时需要——回放格式确定时再议。
- 范围查询用 boundary 事件（turn/round/phase 已是事件）定位起点 + 区间过滤。

### 2.3 因果模型（已确认方向）

- **显式字段为主、栈查询为辅**（沿用 `事件系统基础思路.md` 的分工表）：高频确定因果用
  cause/source 字段，低频特定需求用 `getParent`。
- 奸雄因果误归（TODO 已知问题）的修复 = 规则层给 `damage.source` 显式赋值，不动事件系统。
- end_id 区间是第三种查询形态："此事件期间发生过什么"。

### 2.4 收尾钩子（已确认方向）

- **单 clear 钩子**：事件定义方注册 clear，挂进 `execute` 的 finally、弹栈前执行——
  覆盖正常/被取消/被杀/GameOverError 全部路径。
- **暂不采用 FreeKill 的 exit/clear 两阶段**：那是协程 close 语义逼出来的，
  async/await + finally 没有这种语义；之后若需要再改，改起来轻松。
- 执行顺序（做历史时）：clear → 定稿 end_id → 弹栈（FreeKill 同款顺序，
  保证历史里查到的子树是已清理完毕的完整区间）。
- 技能侧临时 handler 清理用**可逆注册**（disposer）——与第一节插件话题
  "可卸载硬要求"是同一原则在事件域的体现。

### 2.5 中断语义（方向）

- 整局打断：GameOverError 保持现状（finally 弹栈 + clear 钩子已覆盖收尾）。
- 局内"中断结算链"：记 FreeKill 的 interrupted/killed 双标志 + "标记后按栈序自动清理"
  为候选建模；出现真实用例再议。

### 2.6 事件结果收据与 modify/transfer 协议（方向，实现时再讨论）

- 两项目先例：无名杀 `Result`/`forResult`（结构化结果对象）、FreeKill `exec_ret`。
- 方向：收据进历史记录（可回放、可追溯"意图经技能链修改后实际发生了什么"）；
  modify/transfer 协议使订阅者修改可追溯（当前 handler 直接改 data 的过渡方案继续用）。
- 实现细节留到实现时再讨论。

### 2.7 开放问题（实现时讨论）

3. 哨兵与回放格式（回放议题）。
4. 局内中断结算链（interrupted/killed）的真实用例与建模。
5. 全量历史的内存与序列化形态（与回放快照一起定）。
