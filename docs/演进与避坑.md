## 一、内容生态与扩展系统

### 1.1 定位与基本约束（已确认）

- sgs 支持**社区内容**，自定义可以成为玩法的一部分 → 需要模块与插件机制。
- **隔离 = 模块隔离，不做运行时沙箱**：信任社区（无名杀路线的信任前提），
  不采用 JS/Lua 沙箱、受限 DSL 等运行时隔离方案。
- 运行形态：大部分情况**单机**；联机 = **P2P 连房主主机**，服务器（若有）只转发数据、不结算。
  结算只发生在房主端 → 规则引擎保持单机语义，不需要分布式一致性。
- 配套约定：启动插件机制设计时，同步修订 AGENTS.md 的"不提前设计注入接口"一条
  （社区内容即真实消费者，接口设计不再是"提前"）。

### 1.2 两个项目的经验（结论）

- **无名杀之痛**（核心开发者第一手经验）：**隔离性缺失**——API、版本、前后端等各面都没有边界。
  后果：内部 API 被第三方当公共 API 用，核心永远无法自由重构；版本兼容地狱；扩展互相踩。
- **无名杀之资产**：**内置代码编辑器 + 热更新 + 常用技能组合完全不用写代码**。
  新手接触主要玩法的门槛极低——这是无名杀生态能长出来的根本原因。
- **FreeKill 之教训**：控制住了 API 但没有低门槛入口（无内置编辑器，内容要写 Lua），
  社区生态一直起不来。
- 推论：**低门槛的表达面与强隔离的边界必须兼得**，且两者不能走同一条无约束通道
  （无名杀的问题是两者耦合在同一个"随便改全局"的层里；FreeKill 则是把两者一起收紧了）。

### 1.3 插件机制：DI 模块替换（方向，细节重构时定）

核心思想：想改什么就把**整个模块替换掉并重建依赖图**；只要符合接口就改不坏。

参考 DeepSeek Harness（Cordis 模块框架），值得借鉴的 5 件事：

1. **服务即契约**：经容器 key 提供/获取服务，不 import 具体实现——依赖方只见接口。
2. **inject 声明依赖**：加载顺序由"你需要什么服务"表达，而非手动装配序列。
3. **整体替换语义**：替换整个单元，不做字段级 deep-merge；替换后依赖图按服务名重新解析。
4. **可逆注册**：一切副作用注册（监听器、内容登记）带 disposer，卸载/重载可干净撤销
   ——这是热更新的地基。
5. **配置即清单**：条目列表可序列化、可溯源（谁提供谁 / 谁改了谁）、可快照复现；装载失败 fail-loud。

不借鉴（太重）：YAML 表达式引擎、profile/bundle 多层补丁、isolate realm 分组、进程级诊断框架。

sgs 轻量版骨架（示意，非实现设计）：

```ts
// 公共面 = 一组 service 接口（TS 类型即契约）
interface EngineServices {
  rng:      { shuffle<T>(xs: T[]): T[]; seed(n: number): void };  // 换它 → 种子回放
  content:  { heroes: ContentProvider; cards: ContentProvider };  // 内容插件挂这里
  turn:     TurnModule;    // 换它 → 新模式
  respond:  RespondModule; // 换它 → 改响应规则
  life:     LifeModule;    // 换它 → 改伤害/濒死
  victory:  VictoryModule; // 换它 → 身份场/自定义胜负
  decision: DecisionModule;// 换它 → 真人/前端接入
}
// 插件声明：{ provides: 'rng', replace: true, inject: ['content'], apply(ctx) {} }
```

- **两层插件、两种语义，显式区分**：
  - 内容贡献（社区主力：武将/卡牌/技能）→ 挂在 `content` 服务上**增量注册**（append）；
  - 模块替换（机制作者）→ 对整个 service 提供新实现（replace）。
  - 同 service 两个替换 = 装载期显式冲突报错；内容同 id 冲突 = **整单元替换**
    （重定义该武将/卡牌）并记入装载报告——对称地保持"整体替换、不 patch 字段"。
- **容器粒度**（倾向，未定）：应用级一个容器；`Game` 是从容器解析出的局实例
  （事件栈/触发器/玩家状态仍随局隔离，与现状一致）。替换在开局前完成，局内稳定。
- **公共 API = service 接口集**（带 TS 类型）；未声明为 service 的内部函数不可注入
  ——这是对无名杀"内部 API 被当公共 API 用"的直接防御。
- **"可卸载"是模块机制的硬要求**：disposer 齐全才能干净重载，为编辑器/热更新铺路。

### 1.4 降门槛机制（方向，编辑器话题后续另议）

- 表达力分层（L0 免代码数据 / L1 声明式组合 / L2 脚本 / L3 引擎改动）**不是插件机制的主体**，
  而是**降门槛的主要机制**：无名杀式"编辑器 + 热更新 + 免代码组合"是生态生命线。
- 本项目已有地基：`effectRegistry` 的 kind 词汇（L1 词汇表雏形）、`SelectionOption` 的
  label/group/prompt（声明式 UI，插件内容不碰渲染层）。docs/*.json 为规划参考数据
  （第八节已定界：不进运行时）；L0 的具体载体（代码生成器 vs 运行时数据）做编辑器时再议。
- 词汇表生长规则（沿用项目原则）：每个词汇有 2–3 个真实用例才进入词汇表，
  且只能由**内建内容提炼**进入——防止插件作者发明引擎无法验证的"伪词汇"。
- 与 DI 的关系：模块可卸载 + 内容可热载 = 编辑器即时生效的技术前提。

### 1.5 回放与联机一致性（方向）

- **对局配置快照**：`{ apiVersion, content: [{id, version}], overrides: {service: pluginId}, seed }`
  序列化 + hash。
- 回放：**确定性重演**（第七节已定）——配置快照 + 选择日志 + 种子重跑引擎；
  DSH 的 snapshot replay 思路只借鉴"配置快照"部分。
- P2P 联机：房主广播配置 hash，不一致即拒绝或同步；结算只在房主端。

### 1.6 开放问题（重构时确认，勿提前定死）

1. 容器粒度：应用级容器 + 每局实例，还是每局全量容器？
2. 第一版 service 切分：候选 rng / content / turn / respond / life / victory / decision；
   切分原则"有真实替换需求才立 service"。
3. replace / extend 双语义与冲突策略的实现细节。
4. DI 化时机：标包收尾后立刻做，还是军争/神话再临作为第一批内容插件接入时顺带做
   （把内容接入当 DI 的第一个真实用例，符合"有例子再抽象"）。
5. 公共 API 的冻结/版本化策略（semver？弃用期？）。
6. 编辑器/热更新的具体承载（web UI？Monaco？与"真人/前端接入"的关系）。

## 二、事件系统：历史 / 因果 / 收尾

> 本节涉及无名杀 `apps/core/noname/library/element/gameEvent.ts` 与
> FreeKill `lua/server/gameevent.lua`、`lua/server/gamelogic.lua` 的事实均已逐源码核对。

### 2.1 两个项目的经验（结论）

**无名杀**：
- **显式历史树**：`parent` + `childEvents[]`（每事件记录全部子事件）+ `next` 兄弟链 + `after` 插队。
  成因：`waitNext`/`insert` 调度把事件树与 JS 调用栈解耦，栈不再是可靠的父记录，被迫显式维护树。
- **无清理钩子**：`finish`/`cancel`/`neutralize`/`untrigger` 终止语义互相纠缠、与技能实现和
  step-dsl 残留耦合；临时状态全靠技能自己记得清理。
- 字段无隔离：`[key: string]: any`，UI 选择状态（filterButton/selectButton/ai…）也挂在事件上。
- 历史：事件 `start()` 时 push 进全局 "everything" 数组；`player.getHistory` 按 `event.player`
  过滤；无 id/end_id。
- 杂项坑：`getParent` 找不到时返回 `{}` 假对象（静默错误源）。

**FreeKill**：
- **DFS 时间戳**：递增 id + 完成时定稿 `end_id`（无子事件则 = id）+ 全局数组哨兵标记子树终点
  + 按类型索引（event_recorder）二分查询。
- **四主流程按事件类型绑定**（prepare/main/clear/exit 四张表，非发布订阅）+ 按实例
  extra_clear/extra_exit；生命周期 ready→running→exiting→dead；`interrupted`/`killed` 双标志。
- **clear 走独立不可中断的 ClearEvent**：先 clear + extra_clear → 再定稿 end_id → 最后出栈；
  exit 在主协程 main 正常返回后执行，被 `__breakEvent` 打断时协程被 close、exit 不跑、clear 必跑
  （两阶段是协程语义逼出来的）。
- 中断：`breakEvent` 让出 "__breakEvent"，调度器把栈上到目标事件全部标 `killed`，之后按栈序自动清理。
- 查询：searchEvents / getEventsOfScope（Game/Round/Turn/Phase 边界）/ getEventsByRule /
  findParent（含继承匹配）；`specific_events_id`（Damage 单独编号，支撑"第 N 次伤害"）。

### 2.2 历史存储模型（已确认）

**决策：DFS 时间戳法（FreeKill 式），不构建显式历史树。**

取舍理由：
1. **查询形态匹配**：三杀技能的历史需求几乎全是"范围 + 类型 + 谓词"（无双/裸衣/克己/奸雄），
   正是区间查询的甜点；"枚举全部子事件"这类纯结构查询在引擎内直接有调用栈，不需要查历史。
2. **正确性前提免费满足**：时间戳法要求执行严格栈纪律——正是本项目"事件即函数调用"的核心主张；
   `GameEvent.execute` 已有"构造与执行必须同上下文"的运行时校验。
3. **扁平数组 = 回放流**：append-only、可直接序列化；无名杀的树是可变图
   （next/after/联机 `_modparent` 改写父指针），忠实回放还要先拍平。
4. **中断下仍闭合**：被打断的子树照样定稿 end_id，历史里依然是合法闭区间；
   我们的 finally 使 end_id 定稿只有唯一退出点，结构性保证不漏。
5. **成本最低**：一个计数器 + 一个数组；无名杀选树是被调度解耦逼出来的，我们没有那个因。

**红线**：一旦引入"延迟执行/插队"的真实用例（破坏 DFS 序），必须先回头补显式树——
在此之前时间戳法会静默失效。写死这条，防止在不理解前提的情况下引入调度解耦。

**保留 parent 链**：`getParent`（因果/边界定位）继续可用；时间戳数组是历史查询的权威存储，
两者并存、分工不同。

**历史全量保留**（不做活窗口裁剪）：不仅有本回合计数技能，本轮、本局游戏计数技能很快会出现。

落地要点（方向）：
- `history: GameEvent[]` + 全局计数器；push 赋 id，finally 定稿 end_id（无子事件则 = id）。
- 按类型索引 `Map<type, ids[]>` 先不做、线性扫描；性能议题（第五节）再评估二分。
- FreeKill 的哨兵条目仅在"从数组还原树、不持有事件对象"时需要——回放格式确定时再议。
- 范围查询用 boundary 事件（turn/round/phase 已是事件）定位起点 + 区间过滤。

### 2.3 因果模型（已确认方向）

- **显式字段为主、栈查询为辅**（沿用 `事件系统基础思路.md` 的分工表）：高频确定因果用
  cause/source 字段，低频特定需求用 `getParent`。
- 奸雄因果误归（TODO 已知问题）的修复 = 规则层给 `damage.source` 显式赋值，不动事件系统。
- end_id 区间是第三种查询形态："此事件期间发生过什么"。

### 2.4 收尾钩子（已确认方向）

- **单 clear 钩子**：事件定义方注册 clear，挂进 `execute` 的 finally、弹栈前执行——
  覆盖正常/被取消/被杀/GameOverError 全部路径。
- **暂不采用 FreeKill 的 exit/clear 两阶段**：那是协程 close 语义逼出来的，
  async/await + finally 没有这种语义；之后若需要再改，改起来轻松。
- 执行顺序（做历史时）：clear → 定稿 end_id → 弹栈（FreeKill 同款顺序，
  保证历史里查到的子树是已清理完毕的完整区间）。
- 技能侧临时 handler 清理用**可逆注册**（disposer）——与第一节插件话题
  "可卸载硬要求"是同一原则在事件域的体现。

### 2.5 中断语义（方向）

- 整局打断：GameOverError 保持现状（finally 弹栈 + clear 钩子已覆盖收尾）。
- 局内"中断结算链"：记 FreeKill 的 interrupted/killed 双标志 + "标记后按栈序自动清理"
  为候选建模；出现真实用例再议。

### 2.6 事件结果收据与 modify/transfer 协议（方向，实现时再讨论）

- 两项目先例：无名杀 `Result`/`forResult`（结构化结果对象）、FreeKill `exec_ret`。
- 方向：收据进历史记录（可回放、可追溯"意图经技能链修改后实际发生了什么"）；
  modify/transfer 协议使订阅者修改可追溯（当前 handler 直接改 data 的过渡方案继续用）。
- 实现细节留到实现时再讨论。

### 2.7 开放问题（实现时讨论）

1. 事件结果收据与 modify/transfer 协议的具体形态。
2. 按类型索引/二分（性能议题；全量历史下会更早遇到）。
3. 哨兵与历史序列化：已由第七节定（回放 = 确定性重演，不做历史序列化；哨兵仅在存局快照
   需要时再议）。
4. 局内中断结算链（interrupted/killed）的真实用例与建模。
5. 全量历史的内存与序列化形态（与回放快照一起定）。

## 三、状态与位置模型（移动 / 全局状态）

> 本节涉及无名杀牌存储与 FreeKill `lua/lunarltk/core/room/card_manager.lua`、
> `lua/lunarltk/server/events/movecard.lua` 的事实均已核对（无名杀侧由核心开发者口述确认）。

### 3.1 两个项目的经验（结论）

**无名杀**：
- 牌的存放容器是 **nodelist（DOM 节点）**，`position` 是 card 的属性；移动必须显式动 DOM。
- 反直觉的收益：DOM"一个节点只能有一个父"提供了**结构性唯一性**，反而没出过"一牌两份"的岔子。
- 一开始**没有统一移动事件**：lose、gain 等移动事件是分开的 → "处理失去牌"类技能非常麻烦
  （本项目移动模型重构文档引用的正是这个教训）。
- 联机广播 `game.broadcast` 直接传 DOM，序列化问题大（有特殊处理），字段无隔离放大负担。

**FreeKill**：
- **双结构**：区域内容 = id 数组（draw_pile/discard_pile/processing_area/void +
  `player.player_cards[area]`）；唯一性 = 集中索引 `card_place: Map<cardId, CardArea>` + `owner_map`。
  序列化只存数组、加载时重建索引（索引是派生态，不是权威内容）。
- `getCardsByArea` 默认返回**克隆**（对外读的软防线）。
- **语义全耦合进 moveCards 原语**：skillName/proposer/moveMark/visiblePlayers/specialName/
  virtualEquip/extra_data 都塞在移动数据里——不推荐照搬。
- **守恒假设踩坑**：默认牌是守恒的（实际不是）；生成牌靠 printCard 负 id（从 -2 递减），
  销毁靠 Mark 枚举（DestructIntoDiscard 等）改道 Void 区，查不到位置返回 Card.Unknown 手工兜底。

### 3.2 决策：受控容器 CardArea（已确认）

- **观察提炼**：唯一性要么来自物理结构（无名杀 DOM）、要么来自集中索引（FreeKill card_place）；
  裸 TS 数组两者皆无——一张牌对象可以被 push 进两个数组而不报任何错。这是选受控容器的直接理由。
- **CardArea 语义-free**：只负责 进 / 出 / 顺序 / 唯一 / 归属；不掺技能名、移动原因、可见性、
  标记、装备槽位策略（FreeKill 语义耦合的反面）。
- 形态草案：
  ```ts
  class CardArea {
    readonly ids: readonly Card[];   // 对外只读视图
    add(card): void; remove(card): void;  // 内部同步集中索引
    insertAt(card, index): void;     // 牌堆顶/底 = 插入策略，不在位置层
  }
  // 引擎级集中索引（FreeKill card_place 等价物，已确认放引擎级）
  cardIndex: Map<number, { area: CardArea; owner?: Player }>
  ```
  - 容器方法内部维护索引；序列化只存内容、加载重建索引（FreeKill serialize 同款）。
  - `moveCards` 仍是唯一跨容器通道（一次移动一个事件 + reason/mover）；语义封装
    （discard/give/equip…）不动。容器 / 移动原语 / 语义封装三层分离保持。
- **守恒红线**：不做"牌总数守恒"校验——生成（新 id）/销毁/移出游戏（zone 可扩展）是真实需求；
  只校验"一牌一位置 + id 唯一"（测试期 sanity net）。FreeKill 的负 id 与 Card.Unknown
  手工管理要避免。
- **测试也走容器方法**（已确认）：不保留测试专用直写 API——否则牌移动改动后需要额外维护
  并行双通道，心智负担太重。

### 3.3 与事件历史 / 回放 / 联机的关系

- CardMove 是全量历史里最密的记录；统一移动原语保证"本回合/本轮失去过牌"类技能的历史查询可用。
- 容器化 + 集中索引 → 状态快照/序列化便宜（FreeKill serialize 先例），回放与 P2P 联机一致性受益。
- 顶/底仍是取放策略不是位置（既有结论）；`toPosition` 剥离留待移动原语重构时处理。

### 3.4 开放问题

1. `toPosition` 从 moveCards 签名剥离的具体形态（移动模型重构 TODO 既有条目，随重构定）。
2. 实时扫描 `getCardArea` 换成集中索引的落地时机（与容器化同步做）。
3. Void/移出游戏 zone：真实用例出现时再扩展 `CardLocation`（union 加 zone 成本低）。
4. 对账不变量（一牌一位置 + id 唯一）作为测试套件的具体落点。

## 四、玩家决策与 AI 分层

> 无名杀侧事实由核心开发者口述 + `game/check.js` 核对；FreeKill 侧 `lua/server/request.lua`
> 已逐行核对，`lua/lunarltk/server/room.lua` 的 askTo\* 清单与 `lua/compat/askfor.lua` 已核。

### 4.1 两个项目的经验（结论）

**无名杀**：
- **选择零封装**：选择条件（filterButton/filterCard/filterTarget…）裸挂在事件字段上；
  `game.check` 按条件刷新 UI 状态（直接操作 DOM 的 selectable/selected class + `ui.selected`）；
  循环 = check + pause 开窗 → 点击时 ui.click 刷新 check → 确认/取消后 uncheck + resume，
  结果注入 `event.result`。
- **流程固定**：button → card → target → confirm，可跳过步骤但**不可自定义顺序**
  （如 button → target → card 表达不了）。
- 主动技能靠 `backup` 旧条件、注入技能条件、取消则 `restore`——UI 状态与规则状态混在
  同一事件上，嵌套 ask 的状态管理之痛由此而来。
- **AI 接管 = 把 result 赋值为 "ai" 字符串**，之后手动处理 ai 函数调用——规则与 AI 纠缠的实证。
- **录像非常简陋**：在调用动画方法时记录动画内容和时间戳，与选择无关——回放必须重跑
  游戏逻辑，且录像模式下 `trigger()` 直接跳过。

**FreeKill**：
- **Request 是通用基础窗口**（服务端）：command + 按玩家的 data（cbor）+ default_reply +
  timeout（烧绳）+ winners/overtimes；协程 yield 等待；n 个肯定回复即提前结束，其余
  `__failed_in_race` → 落 default_reply；**AI 是挂在玩家对象上的 `player.ai`（makeReply）**，
  服务端计算，人类全回复完或超时后 AI 才回答（避免 AI 抢答泄密）；`__cancel` 语义 + 投降检测。
- **AskTo\* 33 个业务封装** + `askfor.lua` 旧 API 兼容层（askForXxx 全部 deprecated）——
  分层是对的（通用窗口 + 业务工厂），但工厂随业务场景膨胀，**连单技能都长出专属 askTo**
  （askToPoxi / askToGuanxing / askToYiji / askToMoveCardInBoard）。
- 请求对象可序列化，UI 完全在客户端；服务器只发 command + data。

### 4.2 决策与红线

- **选择模型保持现状**：`SelectionOption/Step/Plan/Session` 的抽象度已高于两边
  （无名杀零封装、FreeKill 工厂膨胀）。步骤可组合（有序、依赖前序答案、回溯）——
  无名杀"流程固定不可换序"的反面；技能专属选择 = 各技能的 `selectionPlan`，
  **天然不需要 backup/restore**（无名杀那份痛是"固定流程 + 条件绑事件"逼出来的）。
- **AI 三层红线**（写死）：
  1. 规则层：canUse / targetFilter / 常驻效果；
  2. 内容默认 AI：`ai.shouldUse` / 优先级 / 选牌策略（随内容包走）；
  3. 决策通道：真人 / 前端 / 更强 AI（DI 的 decision service）。
  **AI 永不进入规则层**——无名杀 `result = "ai"` 是反例；FreeKill 的 per-player AI 对象
  对应我们的"内容默认 AI + 决策通道"两层。
- **真人接入 = 可序列化 DecisionRequest**（方向）：SelectionOption 本就是纯数据，
  决策点升级为"发请求、等回答"，本地默认 AI 只是默认回答者。FreeKill 的 Request
  （command + data + timeout + default_reply）是现成参考；我们 P2P 只需 JSON，不抄 cbor 协议。
  接口形态等前端真实消费者出现时再定（AGENTS"不提前设计注入接口"届时修订）。
- **回放 = 选择日志注入，不重跑 AI**（方向）：决策点答案记入历史（第二节 history 或
  独立 selection log）；无名杀"录像 = 动画记录"是反例。
- **决策与执行分离**保持：ask 只决策不执行牌（无名杀 chooseToUse 既决策又执行是反例）。

### 4.3 开放问题

1. DecisionRequest 的具体形态与注入点（做前端时定，与第一节 decision service 联动）。
2. 选择日志并入历史的具体格式（与第二节开放问题联动）。
3. 会话快照（断点续答）：方向已明——我们的会话本就是纯数据（plan 是函数、答案可序列化），
   快照天然干净；实现细节待前端。
4. 超时/托管（烧绳）语义：FreeKill 的 timeout/default_reply/托管给 AI 记下，P2P 联机议题再定。
5. askTo\* 工厂膨胀的防线：新业务场景优先组合既有 SelectionPlan 步骤，禁止单技能专属
   引擎原语（"有例子再抽象"原则在决策层的落点）。

## 五、触发顺序与性能

> 无名杀 arrangeTrigger 执行（`content.ts` 3948-4009）与 FreeKill `skill_table`/`skill_priority_table`
> （`gamelogic.lua`）均已核对；性能结论来自核心开发者口述。

### 5.1 两个项目的经验（结论）

- **性能共识**：结算运算量在两个项目里都不是性能主角（远快于动画，无体感）。
  真正的性能要点只有两条：**(1) AI 的时间复杂度**；**(2) 结算代码不要读 DOM**——
  无名杀最主要的性能开支就是读业务内容时要读 DOM（牌是 nodelist 的直接后果）。
- **无名杀**：大部分事件自带 trigger，实际跑时多数 trigger 是空的 → 加 **hookmap 让空 trigger
  提前返回**。执行顺序按座次（doingList）；**同角色同优先级由玩家手动选择先发动哪个**
  （`chooseControl("选择下一个触发的技能")`，arrangeTrigger content 已核）；silent/无翻译技能
  自动优先；firstDo/lastDo 不参与优先级选择。
- **FreeKill**：时点 → 技能表（skill_table）+ 该时点优先级降序表（skill_priority_table）
  ——索引思想与我们一致。

### 5.2 决策与红线

- **红线：排序必须显式，不得依赖注册/导入顺序。** 标准规则（两游戏一致）：同一时点按角色
  逆时针（座次主排序）；同角色同优先级由玩家手动选择先发动哪个。我们当前"注册顺序 = 导入
  顺序"是巧合行为。最小实现方向：座次主排序（遍历骨架已有）+ 每角色技能列表顺序 +
  同优先级询问（ask 原语已有）+ 锁定技标记（TODO 既有）。无名杀 firstDo/lastDo/getIndex 不抄
  （无真实用例）；FreeKill skill_priority_table 等出现真实"优先级技能"时再实现。
- **性能立场**：结算本身不做性能优化（两项目共识）。只守两条：
  - AI 复杂度意识（AI 是唯一可感知的计算）；
  - **规则代码永不读 DOM/渲染层**——无名杀的教训；我们 headless 架构天然成立，写成红线防回退。
- **规模优化方向**（时机：军争/神话再临 + 插件生态出现性能信号之后）：
  - 内层倒排"技能 → 拥有者"，消掉 handler 内 O(玩家数) 的 `hero.skills.includes`；
  - 空触发提前返回——我们 triggerSystem 按事件名分桶已等价于无名杀 hookmap，保持；
  - 全量历史的内存与查询成本一并评估（与第二节联动）。
- **保持：触发不产生子事件。** 无名杀每 trigger 一个 arrangeTrigger 子事件是历史噪音的根源；
  触发过程不进历史，"技能是否发动"走第四节的选择日志。

### 5.3 开放问题

1. 排序策略的真实用例清单（奸雄/反馈等同点冲突）；实现时按"行为保持"原则显式说明行为变化。
2. 性能基准触发点（技能数/事件数阈值），到时再上倒排。
3. "同优先级玩家手动选"的 UI 形态（选择系统既有原语可表达，与 DecisionRequest 联动）。

## 九、技能建模（技能抽象 / 注册 / 生命周期）

> 无名杀侧事实由核心开发者口述 + `content.ts`（chooseToUse/useSkill/createTrigger）、`player.js`（useResult）
> 核对；FreeKill 侧 `ltk/core/skill.lua`、`skill_skeleton.lua`、`skill_type/active.lua`、`button.lua`、
> `trigger.lua`、`lua/core/trigger_event.lua`、`ltk/server/room.lua`（askToUseActiveSkill）及
> `packages/standard/pkg/skills/biyue.lua` 均已核对。

### 9.1 两个项目的经验（结论）

**无名杀**：
- 先有技能再有效果 → 效果的基础单位是技能，裸效果（全局/临时）与聚合多效果技能实现不便
  （裸效果伪装成 `_` 前缀全局技能；聚合靠 `group` + `expandSkills`；命名空间靠 `subSkill` 拼
  `mainSkillID_subSkillID` 字符串）。
- 技能**裸读字段**：一个对象同时满足多个接口就能在多个场景生效（主动 enable + 触发 trigger +
  常驻 mod），混乱。
- 技能全静态、无实例：临时数据存 `player.storage`，`init`/`onremove` 钩子补偿生命周期。
- 技能集合多通道：skills / additionalSkills / tempSkills / hiddenSkills / invisibleSkills / global。
- 发动流程分裂：主动技 chooseToUse → useResult → **useSkill 或 useCard 两条路径**（转化牌走
  useCard）；触发技 createTrigger 内 cost 事件选牌支付后**直接建事件跑 content，不走 useSkill**；
  "发动技能时"时点（useSkill trigger）只覆盖主动技；无统一打断语义。

**FreeKill**：
- **skill → effect 是后来拆的，代价非常大**（历史遗留 createXXXSkill、技能主效果、group 关联技能）。
  当前：`createSkill` 建骨架（SkillSkeleton），`addEffect` 加效果（11 种类型：distance/prohibit/
  atkrange/maxcards/targetmod/filter/invalidity/visibility/active/cardskill/viewas）；
  **效果只能存在于技能上，没有裸效果**（全局效果靠 `global`/`mode_skill` 技能打补丁）。
- 技能同样全静态：`cost_data` 访问被元表绕到 `room.skill_costs`、`times` 写在静态对象上、
  失效状态 = `player.mark[InvalidSkills]` 前缀匹配——定义与局内状态混淆的实证。
- **frequency 标签膨胀到 21 个**，且互相包含语义已出现（Compulsory 含 Wake/Contract）。
- **can_trigger/can_use 无包装**：通用限制（target == player、hasSkill、phase == Finish）作为
  模板代码写死在每个效果里（闭月实证）——想绕过某条通用限制就处理不了。
- **统一"发动技能"通道**：触发技 cost 后经 `room:useSkill`（SkillEffect 事件）包效果；
  主动技走 AskForUseActiveSkill（客户端选择）→ onCost 整理 → onUse。中断语义统一在
  TriggerEvent 层（broken / trigger_break / breakCheck / killed）。

### 9.2 决策：技能模型（已确认）

- **skill → effect 是对的**：效果 = 一等公民（时点 + 条件 + 行为）；技能 = 效果的命名集合
  （包装器）+ 元数据（frequency/显示/描述）。sgs 现状已是效果散落（effectRegistry/conversions/
  equipTrigger/两个技能注册表）——缺的是统一的效果概念；**与插件机制的 content service 一起
  收口定界**（FreeKill 事后拆的教训：拆得太晚）。
- **裸效果是真实需求**：常驻 kind 词汇、装备效果、临时效果（裸衣现状）、未来全局/模式效果。
- **定义静态 + 局内实例**：定义层（内容模板：效果集合、tags、规则函数）静态共享；局内状态
  （次数、限定技是否已用、失效标记、来源归属、临时数据）归属**局内技能实例**；获得/失去 =
  实例创建/销毁（钩子退化为构造/销毁器，与 DI 可逆注册同构）。先例：createGame 的 hero 副本。
- **frequency 词汇最小化**：只保留锁定/限定/觉醒/转换等核心词进引擎，其余用结构化字段或
  内容层标记（FreeKill 21 标签的反面；第一节"词汇只能由内建内容提炼进入"红线）。
- **可组合谓词**：canTrigger/canUse 必须是可组合的谓词组件（我们的 `subjectIsOwner` 已是雏形），
  通用限制作为组合层而非模板代码——场景想绕过某条限制 = 换一个组合，而不是改不了
  （FreeKill 闭月写法的反面）。

### 9.3 发动流程（方向）

三国杀规则文本几乎不显式分离"先选择"与"再发动"——选牌选目标就是发动；但"发动"作为概念
存在（日志、次数限制、useSkill 时点、防止/打断）。三阶段、一个锚点：

```
① 选择会话（SelectionSession，可回溯、可序列化）
   是否发动 → 选牌（= 选支付物）→ 选目标 → 选项…… → 产出完整发动方案 answers
② 支付 + ③ 效果执行 —— 同一个 SkillUse 锚点事件包裹（触发技与主动技统一）
```

- 计数、`useSkill` 时点（before/after）、打断（`useSkill.before` 置 cancelled，沿用 damage/
  targeting 惯例）、日志声明全部挂在锚点上——学 FreeKill 的统一通道，补无名杀"触发技无
  统一发动时点"的缺口。
- **支付不独立成阶段**：支付内容在①里已选好，②③只是机械执行。两项目把 cost 独立建模
  （无名杀 cost 事件、FreeKill cost 函数）正是"选择与发动耦合"的根源。
- 触发技发动 = 只含"是否发动 + 效果参数"的微型会话，同一锚点；第五节"同点冲突玩家手选"
  自然落在选择会话的一个步骤上。

### 9.4 基础操作清单（结论，业务梳理）

引擎需要支撑的基础操作（两项目交集 + 你梳理）：

1. 技能的获得与失去（获得/失去时栈上仍有 trigger 需额外处理——无名杀 addtrigger 场景）；
2. 技能失效/复原（临时失去效果，**不触发生命周期钩子**）；
3. 技能使用次数/特殊限制（如每项限一次）；
4. 刷新技能（刷新失效状态和使用次数——FreeKill refresh/late_refresh）；
5. 技能抗性（失效判断之前），如锁定技抗性、持恒技抗性；
6. 效果锁定发动（无法取消）——一般只有第一次选择会话（是否发动/cost）有此限制，内容内没有；
7. 效果自动发动（默认正收益技能，如英姿——建议**前端处理**，不建引擎机制）；
8. 技能的隐藏与展示（国战暗置武将牌）。

组合语义（标签 = 基础操作组合，不新增引擎机制）：

- 主公技 = 身份场获得条件；锁定技 = 锁定发动 + 锁定技抗性；觉醒技 = 锁定发动 + 发动后失效
  至局终 + 锁定技抗性；限定技 = 发动后失效至局终；转换技 = 双效果、每次发动后切换。

不抄：无名杀的 tempskill/additionalskill/invisibleskill 三通道（方便性/历史原因）；
**两项目都在发动前检查 `player.hasSkill`，不推荐**（invisibleSkill 需求的根源）。

### 9.5 装备效果（结论）

- 两项目都把装备效果建模为**技能而非裸效果**：存在生命周期语义 + 需要存东西（木牛流马）。
- sgs 的 `equipTrigger` 并入统一效果模型时，保留"生命周期 + 局内存储"能力。

### 9.6 开放问题

1. 效果统一收口的时机与形态（与 DI/content service 一起设计）。
2. 技能实例化（定义静态 + 局内实例）的重构时机。
3. SkillUse 锚点事件的落地细节（触发技/主动技统一、打断语义）。
4. 可组合谓词层的形态。
5. 隐藏/展示（国战暗置）的真实用例——等模式系统。
6. FreeKill 的 max_use_time 四层时间范围作为"技能通用元数据"候选（与第二节"本轮/本局计数"
   呼应），实现时再定。

## 七、多人 / 网络 / 回放

> 无名杀侧事实由核心开发者口述 + `gameEvent.ts` send() 核对；FreeKill 侧 `request.lua`、
> `room.lua`（AskTo\*）、`card_manager.lua` serialize 已核对。

### 7.1 两个项目的经验（结论）

**无名杀联机**（核心开发者口述）：
- **只有主机有完整事件树；客机只同步显示内容和选择条件，不结算。** broadcast 里大部分内容
  是播放动画和同步 player.storage；`_modparent` 等事件关联信息是为了在客机上重现选择 filter
  的条件（修正早期印象：客机不重跑结算）。
- **随机数同步、断线重连、中途加入、双端不一致排查——全部缺失**；断线重连只同步最基础的
  信息，bug 非常多。
- 录像 = 动画 + 时间戳记录，与选择无关（`_status.video` 下 trigger 直接跳过）。

**FreeKill**：
- C/S 每房间一个服务端；Request 带 timeout（烧绳）/托管 AI/投降检测/`_observers` 视角切换
  （旁观、一控多）；`notifyMoveCards` 发前把 player 对象转 id；`moveVisible`/`visiblePlayers`
  控制可见性；客户端 `card_tracker` 做记牌器；`card_manager.serialize` 快照（数组权威、索引重建）。

### 7.2 决策

- **客机 = 纯视图 + 决策输入，不结算**（无名杀同样的分工，我们做成结构性的）：房主独占
  事件树与结算、独占 RNG；客机只收 (a) 事件流（渲染日志/动画描述）+ (b) 决策请求（玩家输入）。
  无名杀的痛点不在分工，而在实现——事件序列化靠字段搬运 + 断线重连缺失；我们的 typed data +
  声明式 UI（第四节）让"发什么"变成结构化的。
- **回放 = 确定性重演（重跑引擎），不做快照式记录**（已确认）：
  - 事件系统与 JS 栈/await 绑定，快照难做（局部变量、中间状态不可序列化）；重演门槛低。
  - 重演的三个前提：**引擎确定性**（红线：RNG 种子化——第一节 rng service；规则代码禁止
    Date.now/Math.random/隐式随机；Map/Set 依赖插入序——JS 已保证）；**配置快照 + 选择日志**
    （第一节 + 第四节）；**版本管理**（内容包版本 + 引擎 apiVersion + 第一节的公共 API 冻结）。
  - 与第二节联动：历史全量保留仍为运行时技能查询服务；**回放不序列化历史**，哨兵与
    历史序列化需求相应弱化（仅存局快照需要时再议）。
- **可见性最小模型**：CardArea 级可见标志（区域对某玩家可见/不可见——无名杀同款做法，
  "可见性是固定的，只要声明 cardArea 是否可见"）；记牌器（明/暗牌进出区域 + 展示牌置信度
  更新）先不做。
- **旁观/切换控制**：需要**玩家与角色分离**（玩家 = 人类席位，角色 = 游戏内角色），
  细节之后再说。
- **烧绳/托管**：在选择窗口（DecisionRequest）上直接加（FreeKill Request 的 timeout/
  default_reply/托管 AI 概念），成本低。

### 7.3 开放问题

1. 重演的版本管理细节（内容版本锁定、apiVersion 演进——与第一节公共 API 冻结联动）。
2. 引擎确定性的验证手段（双跑一致性测试）。
3. 玩家/角色分离的建模（旁观、切换控制、一控多）。
4. 存局快照（非回放用途）：序列化形态（CardArea 数组权威 + 索引重建）与使用场景。
5. 记牌器（用例出现再议）。

## 八、数据驱动与内容边界

> FreeKill 包结构（`packages/*/init.lua`、`pkg/`、`i18n/`、customPages）已实地查看；
> 无名杀工具链事实由核心开发者口述。

### 8.1 两个项目的经验（结论）

- **无名杀**：内容即 JS 代码（character/card/mode），无打包（ES5 单文件、数据格式奇怪），
  工具链只有基础 tsc/eslint/prettier，类型检查靠函数签名/声明类型（apps/core/typings）；
  **不支持 i18n**；扩展覆盖 = monkey-patch lib 对象。
- **FreeKill**：内容全代码——`packages/<pkg>/` = init.lua（入口，返回 Package 实例）+ pkg/
  （武将/技能）+ **i18n/（zh_CN/en_US/vi_VN Lua 翻译表，按包存放）** + audio/image 资源 +
  **customPages（UI 页面声明，QML uri 写在包里）**。存在"覆盖安装 aux_skills hack"与
  UsingNewCore 迁移 shim——结构仍在变动；内容散在代码里、没有单一可导出的数据面（导出不便）。
- **共同点**：内容即代码、翻译与内容分离；差异在 i18n 形态（无名杀没有、FreeKill 按包 Lua 表）。

### 8.2 取舍框架与决策（已确认）

**框架**：spring（XML→JavaConfig）、eslint（eslintrc→flat config）、blockly（JSON→JS API）的
回归规律——**配置一旦需要引用代码或包含逻辑，代码配置全面胜出**（JSON 路线要自建 schema/
引用解析/校验/IDE/重构两套系统）；数据文件只在**纯数据、无代码引用、需外部工具消费**时赢。

**决策**：

- **内容定义 = TS 代码**（现状保持）：武将/卡牌定义引用效果函数——全是代码引用，注册表模式
  就是代码配置。军争/神话再临接入 = 新内容包 TS 代码，不是 JSON 装载。
- **牌堆 = 纯数据**：无引用、规格规整、可由工具/AI 生成——`src/standardDeck.json` 保持；
  军争牌堆接入时统一格式（docs 里那份只是规划）。
- **docs/*.json = 规划参考**（从无名杀导出的定义），**不进运行时**。
- **规则文本 info**：进 TS 定义（`SkillDef.info`/`CardDef.info`），内容源 = docs 导出数据
  （开发期复制/生成）；显示文案集中，不为此建运行时数据层。
- **i18n**：单语先行（无名杀不支持 i18n 也活得很好）；文案集中即可，不为多语言预付款；
  真有需求时再参考 FreeKill 按包翻译表。

### 8.3 开放问题

1. **L0/内置编辑器的载体**（代码生成器 vs 运行时数据）：等实际做编辑器时再讨论——
   涉及序列化与重新编辑的问题。
2. **内容包与前端 UI 的边界**：FreeKill 的 customPages 让内容包耦合前端 QML；
   我们"插件不碰渲染层"的红线如何与"修改前端内容的需求真实存在"调和——
   等前端架构讨论时定，暂不写死。
3. 军争/神话再临以 TS 内容包接入时的具体组织（与第一节 content service 联动）。
